## 必须遵守的实施边界

1. **默认使用官方未修改引擎；修改须逐项事先获批。** 固定程序、提交、游戏构建、热修数据和摘要，保留可复现的官方原版基线。用户允许提出引擎修改方案，不等于已授权任何具体补丁；未获同意前不得修改源码、编译或启用修改版，也不把研究构建自动加载为运行版本。
2. **优先修正本项目必要的输入、调用和展示。** 保留完整角色与装备编码；字段转换、百分比单位和明确的面板格式化必须有对应依据及检查，不能用修正系数追平结果，不能把引擎规则改动放到应用层规避审批。
3. **如实处理不支持的专精。** 若官方原版或 Raidbots 拒绝某专精，记录实际错误和影响，按下述审批流程提出处理方案；不静默改职责、不冒用其它专精的报告。不支持项未解决前，不宣称该职业或全职业完成。
4. **报告重放与产品预览分开比较。** 原报告保留其增益和战前条件；产品无临时增益预览先在原版中使用相同条件计算，再比较应用。样本不要求预先证明无增益，先计算、比较，再定位差异。
5. **逐个职业闭环，不并行铺开各职业。** 从已有原型支持的死亡骑士开始，一个职业的全部专精完成验证后再进入下一职业，其余按当前版本官方职业编号顺序推进。当前职业缺报告、仍有差异或等待引擎修改批准时明确记录阻塞，不擅自跳过或视为通过。检查通过后继续下一职业，无需逐职业再向用户请求普通实施确认。
6. **以 Raidbots 配对数据验证接入。** 使用真实报告的完整输入和同一报告的属性结果；英雄榜及自行生成的数据不能替代其期望值。少量游戏证据只用于 Raidbots 覆盖不到的明确缺口，不作为重新扩大采集的前置条件。

## 引擎修改的事先审批

- 先保留官方原版失败的最小输入、Raidbots 对应结果或缺口证据，确认不是版本、配置或应用接入问题。
- 提交具体修改方案供用户审阅：问题与证据、拟修改的文件及规则、影响职业／专精、验证方式和回退办法；说明是否有上游依据及仍存的不确定性。
- **取得用户针对该项修改的明确同意后，才修改、编译和验证引擎。** 扩大到其它规则或超出已批准范围时重新取得同意。普通应用适配不需要重复审批。
- 获批后一次实施一项，保留官方原版对照，记录补丁和运行版本；原失败场景及受影响的已通过职业回归通过后才启用。未验证的实验构建不得作为默认运行引擎。

## 差异处理规则

- 每项差异记录输入、期望来源、实际值、版本及重现命令。输入或适配错误修在本项目共享入口，配一项能重现该错误的检查。
- 不删除失败样本、不改期望值、不放宽精度来获得通过。已有英雄榜快照作为诊断材料，不以其全部匹配驱动私有引擎修改。
- 原版与服务端结果不同，先核对版本和完整配置；同条件仍不同则保留最小复现，不立即修改上游。
- 原版与服务端一致而应用不同，优先检查本项目转换、选项、读取及格式化。
- 原版结果与游戏面板不同，必须先确认测量口径；不得把面板值与战斗效果值混称。明确需要用户操作时，只提出具体角色、字段和一次最小取样。
- 没有新候选或具体失败需要取证时，停止泛化联网检索；资料不足不能写成“已准确”。

- 完整职业、专精、合法种族清单及功能检查都有结果；不能用“能调用”代替数值验收。

- 所有引擎修改均有用户明确批准、补丁记录、原版对照和影响范围回归证据；运行版本可追溯。
