## 0. 给实施者的执行摘要

**产品目标：针对一个具体角色，在指定场景、按键模型和允许动作范围内，搜索模拟表现更好的、能够被真实 GSE 执行的静态序列。**

用户已经确定的工作流不得更改：

```text
游戏内现有插件 /simc 导出
            ↓
本地 Sim2GSE 导入完整角色资料
            ↓
同一 SimulationCraft 引擎计算参考基线和候选序列
            ↓
搜索技能排列、动作块组合、主动饰品调用方式
            ↓
独立复测最佳候选
            ↓
输出 GSE 字符串及报告
            ↓
用户手动导入 GSE，并由用户实际按键执行
```

| 已确定事项 | 实施约束 |
|---|---|
| 不开发新的魔兽插件 | 不增加专用游戏内采集器、通信插件或实时桥接组件 |
| 按具体角色优化 | 保留等级、天赋、装备、套装、饰品及属性信息；不以专精毕业模板代替个人输入 |
| 主动饰品属于核心搜索对象 | 不仅搜索技能频率，也搜索饰品与技能的块内顺序、出现位置和调用覆盖范围 |
| 本地计算 | 不要求账号、订阅、服务器、在线模型服务或第三方模拟网站 |
| 使用真实战斗引擎 | 不用简化的 Python（编程语言）伤害公式冒充 SimulationCraft 的评估结果 |
| 结果必须能落地 | 被模拟的动作序列必须与导入 GSE 后实际编译执行的序列一致 |
| 优先打通可信闭环 | 先验证导出协议和执行语义，再投入搜索算法和界面 |
| 不承诺全局最优 | 对外称“本次预算内找到的最佳候选”，不承诺达到标准循环的某个固定百分比 |
| 首轮最小闭环 | 邪恶死亡骑士、静止单目标、300 毫秒名义输入间隔；不用历史鲜血样本替代，固定多目标留到后续扩展 |

**实施顺序：P0 兼容性核实 → P1 序列与导出闭环 → P2 执行模型 → P3 个性化优化 → P4 终端产品化。** P5 为后续扩展，不能反过来阻塞最小可行版本。

## 1. 产品目标与问题定义

### 1.1 要解决的问题

同一专精的不同角色，可能由于主动饰品组合、套装、天赋、急速及战斗条件不同，适合不同的序列。工具需要实际评估这种差异，而不是预设“每个角色一定需要完全不同的宏”，或“一个毕业宏适用于所有人”。

尤其要把两类个性化区分开：

| 层次 | 举例 | 本项目如何处理 |
|---|---|---|
| 配置适配 | 两个角色的主动饰品分别位于不同槽位 | 正确解析槽位并生成调用命令，这是基础能力 |
| 性能优化 | 双主动饰品顺序、与爆发技能的组合方式改变表现 | 通过相同条件下的模拟比较，证明调整是否带来收益 |

**仅仅替换 `/use 13` 与 `/use 14` 不足以证明优化器的价值。** 报告应展示相对于简单合法序列的实际改善及不确定性。

### 1.2 数学表述

```text
输入：
P = 角色配置
E = 战斗环境及其分布
K = 用户输入节奏及其分布
C = 允许动作、手动动作和执行限制
V = 游戏、GSE、模拟器及数据版本
B = 计算预算

搜索对象：
S = 可编译为真实 GSE 的有限静态序列

目标：
在 C 和 V 的约束下，使用预算 B，寻找期望输出表现较好的 S。
```

产物是 `best_found_sequence`（已发现最佳序列），不是有数学证明的全局最优解。相对于标准动作优先级列表的百分比，只描述当前模拟条件，不能直接解释为实战完成度或角色操作水平。

### 1.3 非目标

不做装备推荐、自动换装、自动选天赋、自动按键、读取游戏进程内存、战斗中实时决策、自动设置目标或焦点、在线账号系统。第一版不支持任意第三方复杂 GSE 字符串的完整模拟，也不搭建序列分享社区。

## 2. 已核实的技术事实与需要纠正的假设

本节的事实依据见文末编号来源。后续章节中的接口、模块、阈值和实施安排属于本项目设计，不表示上游已经实现这些功能。

| 事项 | 实施结论 | 来源 |
|---|---|---|
| `/simc` 的作用 | 导出角色配置，不是导出一个已求得的最优固定循环 | [S01] |
| 标准 APL（动作优先级列表） | 根据当前条件寻找可用动作；不能把普通列表直接视为 GSE 点击序列 | [S05] |
| GSE 执行对象 | 一次有效按键执行一个 Block（动作块）；块可含多条命令，不因当前动作失败而停在该步 | [S02] |
| 非公共冷却动作 | 可以与公共冷却技能组合；因此每条失败的饰品命令不等于浪费了一次独立按键 | [S02]、[S04] |
| GSE 的时间限制 | Pause（暂停块）的时间表达依赖点击计数，不能当作战斗中的可靠墙钟计时器 | [S03] |
| 战斗中条件分支 | 不允许把模拟器对资源、增益或饰品状态的任意判断直接移植为 GSE 实时决策 | [S03]、[S04] |
| 原生单按钮模拟 | SimulationCraft 的暴雪辅助战斗模式不是 GSE 模式；其单按钮公共冷却惩罚不能直接套用 | [S05] |
| 技能队列 | SimulationCraft 提供相关选项，但文档仍提示可能存在问题；必须验证所选版本行为 | [S05] |
| 导出编码 | 本次核查的 GSE 主分支使用 `!GSE3!` 前缀及原生编码接口，链路为对象序列化、压缩和文本编码 | [S09] |
| 标准循环不是数学上限 | 先前研究的鲜血默认动作列表明确不保证绝对最高输出；该历史例子不充当首版邪恶专精的基线，邪恶参考须在 P0 重新核实 | [S08] |

需要废弃的简化设想：

| 不采用的设想 | 替代方案 |
|---|---|
| 按模拟中的成功施法次数直接设置相同比例，便等价于最优序列 | 频率仅用于生成初始候选，优劣由完整执行模拟决定 |
| 每次公共冷却结束才推进序列 | 建立独立按键事件流，公共冷却期间的按键也必须处理 |
| 一个饰品两分钟冷却，因此应在序列中大幅减少其尝试次数 | 比较真实成本；同块附带尝试可能不挤占技能机会 |
| 把饰品放在技能前面就等于与该技能成功释放同步 | 前面的饰品可能成功，后面的技能可能失败或被排队，必须模拟 |
| 去掉手动技能后仍使用标准 APL 免费补放 | 显式建模手动控制，禁止隐藏的理想玩家补全 |
| 有一个看起来合理的百分比就证明方案有效 | 要求独立复测、置信区间、对照组和游戏内语义校验 |

**版本注意：本次读取的主分支不等于用户安装的发布版本。P0 必须把上述证据对应到实际版本和固定提交，不能直接跟随可变主分支发布产品。**

## 3. 第一版范围

### 3.1 最小可行版本的范围

| 维度 | 第一版支持 | 暂不支持或须单独解锁 |
|---|---|---|
| 运行平台 | Windows 本地运行；中文终端与中文路径 | 跨平台安装包、网页服务 |
| 游戏版本 | 用户当前正式服版本；以实际构建号锁定，目标为当前讨论的 12.1 环境 | 所有历史版本、怀旧服、未测试补丁 |
| 职业 | 首先邪恶死亡骑士，使用用户提供的样本 | 鲜血及其他专精；一次性支持所有专精 |
| 等级 | 输入中真实等级，且该等级已通过引擎和动作可用性测试 | 宣称任意等级都可靠 |
| 装备 | 当前装备，保留完整物品修饰数据 | 搜索背包装备组合 |
| 主动饰品 | 已验证模型与执行方式的瞬发主动饰品，包括双主动的使用顺序 | 未验证的引导、蓄力、特殊选点或特殊交互饰品 |
| 战斗药水 | 首版固定关闭，原生参考与候选一致 | 药水使用及选择开关留到后续版本 |
| 动作结构 | 有限顺序循环；块内允许经验证的非公共冷却动作与一个公共冷却动作 | 任意 Lua（脚本语言）表达式、动态条件、复杂嵌套程序 |
| 战斗环境 | 静止单目标，先打通最小可行闭环 | 固定多目标、多场景分布、完整大秘境路线 |
| 优化模式 | 严格序列研究模式 | 手动辅助模式在 P5 解锁后提供 |
| 界面 | 粘贴角色字符串或文件导入、自动运行与中文进度、导入字符串输出 | 逐技能／饰品配置向导、首版药水开关、独立桌面图形应用 |
| 输出 | 一个推荐候选，可附保留候选列表 | 强制同时生成三个营销性质的模式 |

对不支持的主动饰品，不能悄悄当作被动、当作可用、直接删掉或给零分。程序自动报告具体不支持原因并停止相应优化；首版不提供让用户忽略该效果后继续的选择。

### 3.2 严格模式与辅助模式

| 模式 | 游戏内分工 | 模拟要求 | 发布阶段 |
|---|---|---|---|
| `strict`（严格序列研究模式） | 本次选定的主动动作全部由 GSE 序列执行 | 不得由标准 APL 在后台补放；排除的动作确实不执行 | 第一版 |
| `assisted`（手动辅助模式） | 填充动作由序列执行，指定技能或饰品由玩家手动 | 明确手动输入策略、反应延迟和输入预算，双方共享同一角色资源 | P5 |

首版严格模式研究邪恶死亡骑士的输出序列。用户已排除以鲜血坦克专精作为首轮对象；历史鲜血资料仅保留为来源记录，不作为邪恶的角色输入、动作策略或基线。

防御、打断、控场及人工决策能力不属于第一版输出评分。是否将某个兼具输出与防御意义的技能纳入研究，由动作策略显式指定，不能静默决定。

## 4. 总体架构与技术选择

### 4.1 组件划分

```text
中文命令行 / 参数向导 / 进度面板
                 │
           任务编排与本地记录
                 │
     ┌───────────┼───────────┐
     │           │           │
  角色解析    候选搜索      结果报告
     │           │           │
  能力清单    序列中间表示    独立复测
                 │
        ┌────────┴────────┐
        │                 │
   模拟输入生成       GSE 导出适配器
        │                 │
   simc-gse.exe       best.gse.txt
        │
   标准战斗引擎
   + 按键事件控制器
   + 执行轨迹与统计
```

### 4.2 技术栈

下列为默认工程选择；依赖具体版本在 P0 锁定，不追求“最新版本”。

| 部分 | 选择 | 职责 |
|---|---|---|
| 编排语言 | Python（编程语言），选择依赖均支持的稳定版本并锁定 | 输入、任务调度、搜索、统计、导出 |
| 命令行 | Typer（命令行框架） | 子命令、参数类型和帮助信息 [S15] |
| 终端面板 | Rich（终端显示库） | 表格、进度、日志和状态显示 [S16] |
| 配置 | TOML（配置格式） | 用户可读配置，优先标准库读取 |
| 数据交换 | JSON（结构化数据格式） | Python 与模拟器间的版本化协议 |
| 本地缓存 | SQLite（嵌入式数据库） | 任务索引、候选结果、断点恢复 |
| 战斗计算 | 原版 SimulationCraft 的 C++（编程语言）引擎及隔离补丁 | 复用职业、资源、装备和伤害计算 |
| GSE 编码 | 独立编码适配器；必要时使用 cbor2（对象序列化库） | 匹配实际发布版本的导出协议 [S17] |
| 测试 | Python 单元测试与上游兼容的 C++ 测试 | 语义、回归、往返和集成验证 |
| 发布 | Windows 可解压运行目录 | 前端程序、模拟器、清单、许可证和使用说明 |

第一版不引入分布式队列、网络数据库、浏览器前端、模型调用服务或通用插件框架。游戏内 GSE 本身不需要修改。

### 4.3 模块契约

| 模块 | 输入 | 输出 | 不应承担的工作 |
|---|---|---|---|
| `profile`（角色解析） | 原始 `/simc` 文本 | 规范化角色与校验结果 | 重新实现职业机制 |
| `capabilities`（能力检查） | 角色、引擎、GSE 版本 | 动作与饰品支持清单 | 猜测未知效果 |
| `sequence`（序列模型） | 候选结构 | 合法、确定的动作块序列 | 战斗中临时选技能 |
| `engine`（模拟器适配） | 模拟请求 | 原生报告、扩展统计 | 使用假数据补足失败任务 |
| `optimizer`（搜索） | 候选集合与评分 | 已发现最佳候选 | 直接修改角色装备 |
| `evaluation`（评估） | 重复模拟结果 | 对照、区间与稳定性指标 | 把最高一次输出当均值 |
| `gse_codec`（导出编码） | 已验证序列 | 导入文本与往返验证记录 | 执行任意外部脚本 |
| `storage`（本地存储） | 任务与结果 | 可恢复的缓存 | 保存账号凭据 |

## 5. 输入解析、动作清单与版本管理

### 5.1 输入保真

保存原始文件，再生成规范化文件。必须保留的字段包括职业、专精、种族、等级、天赋字符串、当前装备槽位、物品编号、物品修饰编号、宝石、附魔，以及被当前引擎识别的角色相关选项。

| 输入情况 | 行为 |
|---|---|
| 背包物品以注释列出 | 保留在原始输入中，不视为已装备 |
| 物品名称注释缺失 | 不依名称判断物品身份，优先使用编号与修饰数据 |
| 专精、天赋或等级不可解析 | 明确报错，不替换成默认角色 |
| 多个角色或额外模拟任务 | 第一版拒绝，提示只接受单角色导出 |
| 用户自带 `actions` 等动作列表覆盖 | 默认拒绝混入角色导出模式；研究导入须单独显式开放 |
| 指定额外输入文件、远程导入或输出路径 | 不直接透传；禁止输入文件控制任意文件读写 |
| 未识别的非注释选项 | 列出选项及所在行；阻止静默忽略 |
| 物品数据库缺失或效果未知 | 记录缺失项并停止相关评估，不能生成看似正常的效率；已确认沿用的上游被动模型限制按下述边界处理 |

任务 8 结项边界（用户于 2026-09-12 明确）：被动天赋、装备及附魔继续由固定上游引擎处理，本项目不另行补算或修复其机制。当前三个已记录疑点按[执行原型结项报告](sim2gse/execution-prototype.md#结项边界与后续验收)继承模型和提示，可开展离线搜索，不代表疑点已消除或实机收益已验证。此边界不豁免角色解析失败、主动动作映射缺失、不支持的执行类型及本项目新增回归。

接口不得要求战网账号信息。默认使用本地模拟器数据与缓存；需要联网补充数据时，必须有单独、显式的准备步骤，不能在优化中隐式上传角色资料。

### 5.2 能力清单

按用户于 2026-09-12 明确的产品流程：粘贴 SimulationCraft（模拟器）的角色字符串 → 程序自动解析角色并识别能力 → 自动模拟、搜索及复测 → 输出 GSE（按键序列插件）导入字符串。对受支持且有效的输入，整个生成过程不要求用户挑选技能、确认技能清单、填写技能编号或决定饰品使用方式。首版使用已确定的单目标、300 毫秒与严格序列设置；战斗药水固定关闭，不提供药水及逐能力配置选项。原生参考与候选使用相同消耗品设置。

能力清单是程序每次运行自动生成的内部数据。程序依据固定版本的职业／天赋主动标记、当前角色等级、已选天赋、种族、装备及替换关系建立候选，映射至原生执行动作。标准 APL（动作优先级列表）用于核对参考策略及能力覆盖，实际施放记录用于核对与统计，两者都不能代替主动身份识别；单次未使用或开场尚不可用不能成为删除动作的理由。角色、版本或装备变化后自动重新取得，不维护人工逐角色确认的清单。

运行时遇到无效输入、未知动作或未支持的关键物品效果，由程序自动给出具体原因并停止相应优化，不静默遗漏、不要求用户选择忽略后继续，也不输出冒充有效的导入结果。开发阶段的样本调查只用于建立规则与回归用例，不能变成每个用户生成序列时的人工步骤。自动识别器及完整生成流程由后续实施阶段编码实现，本节并不表示它们已经开发完成。

能力清单区分可按动作、状态替换和派生效果：保留真正的主动输出与爆发能力，宠物、疾病及装备被动效果继续由原生引擎处理。尚不能映射的能力必须明确报告，不能删除后仍宣称与完整原生参考等价。当前角色的来源、映射状态及已知模型缺口见[原生动作来源与首轮能力映射](sim2gse/action-capabilities.md)。

每个候选动作至少具有以下信息：

| 字段 | 含义 |
|---|---|
| `action_key` | 项目内部稳定动作标识 |
| `simc_action` | 已核实的模拟器动作映射 |
| `base_spell_id` | 基础法术编号；物品动作则保存真实槽位和物品身份 |
| `replacement_mapping` | 天赋或触发导致的替换关系，必要时由引擎与 GSE 分别验证 |
| `action_kind` | 技能、物品、种族能力、开始自动攻击等 |
| `execution_capability` | 是否触发公共冷却、是否可在施法中使用、是否引导等能力 |
| `target_policy` | 当前目标或明确支持的固定施法目标 |
| `support_status` | 已验证、仅引擎支持、仅导出支持、不支持 |
| `evidence` | 对应源码位置、版本与测试用例 |

动态资源消耗、受急速影响的冷却等应由原生引擎计算，不在 Python 侧缓存成永远不变的数字。

GSE 对基础法术与替换法术有自己的处理逻辑。不能直接把模拟输出里的伤害事件编号全部当成可按的技能编号，也不能依靠中文名字猜映射。[S12]

### 5.3 兼容性锁定

每次任务记录：

```text
工具版本与源码提交
SimulationCraft 上游提交、补丁提交、可执行文件哈希
引擎数据构建号与实际模型版本
GSE 发布版本、对应源码提交、导出格式适配器版本
目标游戏构建号、客户端语言
角色配置哈希、动作策略哈希、场景哈希
输入模型、随机种子集合、线程数与搜索预算
```

升级任一关键项，都必须失效相关缓存并重跑回归。不能只用“12.1”或“GSE 3”作为完整兼容性标识。

## 6. 序列的中间表示

### 6.1 统一表示，避免模拟和导出各说各话

所有候选先转换为 IR（中间表示）。模拟器和导出器都只能消费这份表示，不能各自再修改技能顺序。

以下为**本项目拟定的数据结构**，不是 GSE 的原生导入格式：

```json
{
  "schema_version": 1,
  "sequence_mode": "sequential",
  "blocks": [
    {
      "commands": [
        {"op": "start_attack"},
        {"op": "use_item", "inventory_slot": 13},
        {"op": "cast", "action_key": "example_spell_a", "target": "current"}
      ]
    },
    {
      "commands": [
        {"op": "use_item", "inventory_slot": 14},
        {"op": "cast", "action_key": "example_spell_b", "target": "current"}
      ]
    }
  ]
}
```

此示例仅说明结构；`example_spell_a` 与 `example_spell_b`（示例技能占位标识）不是已核实的技能映射，不能直接用于模拟或导出。邪恶专精的实际动作及饰品能否放入这些块，由角色样本和动作能力检查决定。

### 6.2 编译约束

| 规则 | 要求 |
|---|---|
| 动作块顺序 | 逐块循环；块内命令顺序严格保留 |
| 公共冷却动作 | 第一版每块最多一个会占用公共冷却尝试的动作，包括相关物品动作 |
| 非公共冷却动作 | 可组合，但需验证在公共冷却、施法和引导期间的可执行性 |
| 未知命令 | 拒绝，不执行任意 `/run` 或用户脚本 |
| 条件表达式 | 第一版只生成已测试的简单宏条件；不接受模拟器条件表达式透传 |
| 长度限制 | 按目标 GSE 与游戏版本检查，尤其验证多字节中文文本，不机械套用字符计数 |
| 外部依赖 | 第一版导出自包含序列，不依赖用户已有宏名称或变量 |
| 序列初始位置 | 作为执行语义的一部分；不能在缓存去重时随意旋转整个序列 |
| 重置行为 | 必须与选定 GSE 配置匹配，并在报告中说明跨战斗是否保留位置 |
| 程序压缩 | 可合并等价表示，但不能改变开始阶段或按键展开结果 |

GSE 的块类型、暂停和循环已有官方说明，但本项目第一版只实现经过验证的有限子集。[S03]

### 6.3 明确分离三种频率

| 指标 | 定义 |
|---|---|
| 序列出现频率 | 某动作在编译后序列中出现的次数占比 |
| 按键尝试频率 | 实际输入流中该命令被提交的次数 |
| 成功施放频率 | 最终真正执行的动作次数 |

三者不能互相替代。优化的是最终表现，而不是让其中一个比例看起来接近模拟报告。

## 7. SimulationCraft 执行模型

### 7.1 采用原生引擎扩展

维护一个范围受控的 SimulationCraft 分支，增加 **Input Controller（输入控制器）**，接管目标角色的主动动作选择与提交。职业状态、伤害、资源、冷却、增益、装备特效与被动触发仍由原生引擎计算。

源码研究入口为上游 `engine/player`、`engine/action`、`engine/sim`、`engine/item`、`engine/report` 与职业模块。确切函数和钩子在 P0 审计后确定；本文不虚构已经存在的扩展接口。[S14]

不以原生 `sequence` 或 `strict_sequence` 的名称相似作为行为等价证明。[S05]

### 7.2 两种后端模式

| 后端模式 | 主动动作由谁决定 | 用途 |
|---|---|---|
| 原生参考模式 | 固定版本的标准 APL | 生成参考基线，验证补丁关闭时没有改变原引擎行为 |
| GSE 执行模式 | 独立输入事件流与当前动作块 | 候选序列评分 |

GSE 模式必须关闭该角色原有的主动技能扫描、额外非公共冷却扫描和默认物品自动调用，防止同一技能或饰品被两个控制器执行。自动攻击后续挥击、被动触发和自主宠物行为可按原生机制继续，但启动方式及人工宠物命令须单独定义。

### 7.3 按键事件语义

```text
初始化角色、场景、明确的战前动作与序列状态。

在每个有效输入事件：
    取出当前动作块。
    按规定顺序提交该块中的命令。
    由执行适配层判断是否可提交、进入技能队列或拒绝。
    不转去扫描其他动作块寻找可用技能。
    按已核实的 GSE 步进规则更新序列位置。
    安排下一次输入事件。

在真正的动作执行事件：
    由原生引擎结算资源、公共冷却、伤害与触发。
    把执行结果关联回此前的输入与命令。
```

以上是行为要求，不是可直接调用的 C++ 接口。不能直接调用一个底层伤害函数来绕过正常的可用性、施法、资源与排队流程。

### 7.4 必须处理的边界

| 边界 | 处理要求 |
|---|---|
| 公共冷却进行中 | 输入仍发生；步进不能只在公共冷却结束时更新 |
| 当前技能资源不足 | 本次失败不导致普通 APL 式即时回退到下一技能 |
| 技能排队窗口 | 区分提交、进入队列、覆盖、取消与真正执行 |
| 连续按键覆盖 | 使用目标客户端经验证的行为，不预设所有按键都执行或永远先入先出 |
| 正在施法或引导 | 保留原生行为；不支持的可中断/蓄力机制须明确拒绝 |
| 同一块多个非公共冷却动作 | 按实际顺序处理共享冷却、施法限制和前后效果 |
| 同时刻事件 | 明确资源恢复、输入、队列提交和执行事件的优先顺序 |
| 按下与松开 | 依据实际绑定配置折算有效执行事件，不把同一次物理按键无条件算两次 |
| 战前动作 | 参考组与候选组使用明确、一致的战前策略，不能只给一方免费铺垫 |
| 目标状态 | 第一版固定目标集合；目标选择不能由隐藏最优逻辑代做 |

按键绑定和按下/松开的影响存在版本差异，应以实际 GSE 配置与游戏测试为准。[S13]

### 7.5 输入节奏与延迟

输入模型支持名义间隔、间隔扰动、短暂停顿与初始相位。用户已选定 300 毫秒名义间隔，约每秒 3.33 次有效输入；第一版先以固定间隔调试，但推荐结果必须接受节奏扰动复测。公共冷却期间仍处理输入与序列步进，不能将该设置解释为每次公共冷却只推进一步。

界面上的“按键频率”仅用于模拟用户可实现的实际输入，**不得实现向游戏发送按键的功能**。默认测试值只是模型假设，用户未校准时须在报告醒目标注。

技能队列窗口、网络延迟和输入间隔分别建模，不叠加两套相同延迟。原生 `enable_spell_queue` 与 `spell_queue_window` 可作为研究入口，但不能未经一致性验证直接宣布为真实 GSE 模型。不要启用暴雪单按钮模式的额外公共冷却惩罚来模拟 GSE。[S05]

### 7.6 诊断轨迹

对验证用例和最终候选保留逐事件轨迹；大规模筛选默认只保留聚合指标。

每条轨迹至少包含：时间、输入编号、序列位置、块内命令编号、动作标识、输入前后资源、公共冷却状态、物品冷却、队列状态、提交结果、实际执行时间、拒绝原因及关联输入编号。

拒绝原因至少区分：公共冷却限制、资源不足、冷却未好、目标不合法、当前施法限制、被后续输入覆盖、动作不受支持。不能把“排队成功但尚未执行”直接统计为失败。

## 8. 主动饰品：第一版的核心优化能力

### 8.1 识别与约束

饰品槽位是调用位置，物品编号及修饰信息决定具体效果。换饰品或交换槽位后，旧结果不得继续被标为适配当前角色。

| 饰品情况 | 处理方式 |
|---|---|
| 两个被动饰品 | 保留引擎中的被动效果，不生成无意义的主动调用 |
| 一个主动饰品 | 搜索调用位置、块内前后顺序与覆盖哪些动作块 |
| 两个主动饰品 | 同时搜索两者的优先顺序、同块或分块调用、与技能的组合 |
| 有共享使用限制 | 由具体物品的原生模型处理；不能假设全部饰品共享相同冷却时间 |
| 主动效果改变急速或资源 | 由同一角色状态传播到后续战斗过程，不另写平均属性近似 |
| 引导、蓄力或选点饰品 | 能力与真实按键语义未验证前，不进入第一版搜索 |
| 物品有未支持效果 | 明确列出，不能仅凭物品成功加载就宣布完整支持 |

### 8.2 搜索空间

对每个允许由序列使用的主动饰品，考虑以下有限选择：

| 维度 | 候选选择 |
|---|---|
| 调用覆盖 | 每个适合的动作块、若干指定动作块、单个指定动作块 |
| 块内位置 | 技能前、技能后；是否有效须经过执行适配层验证 |
| 双主动顺序 | 13 → 14 或 14 → 13 |
| 命令组合 | 与技能同块，或在有理由时使用单独动作块 |
| 序列位置 | 不同初始位置和技能排列下的联动效果 |
| 动作包含 | 在用户允许的范围内决定是否纳入；删除主动使用须在结果中显式披露 |

**不搜索无法导出的逻辑**，例如“增益出现时自动用饰品”“冷却剩余 2 秒时切换子循环”或“战斗开始后准确等待 120 秒”。第一版的时间关系来自固定动作序列与真实资源/冷却结果，不来自隐藏计时器。

“频繁尝试一个尚在冷却中的非公共冷却饰品”不应直接受到扣分。只有它确实改变可执行技能、产生有害延迟、占用独立输入或违反其他约束时，才会通过表现或有效成本体现问题。

### 8.3 饰品模式不得由评分偷偷改变

| 配置值 | 含义 |
|---|---|
| `gse`（序列使用） | 主动使用方式由优化器在允许空间中搜索 |
| `disabled`（不使用主动效果） | 本次模拟及导出均不主动使用，但保留装备和被动效果 |
| `manual`（手动使用） | 只有辅助模式及其手动控制器已实现后才接受 |

严格模式遇到 `manual` 必须报错。不能从“序列使用”自动切到“完美手动使用”，然后宣称后者更好。

### 8.4 必须输出的饰品结果

报告至少包含物品身份、槽位、调用方式、尝试次数、真正使用次数、首次使用时间、后续使用间隔、共享冷却拒绝次数，以及与选定爆发技能的实际时间关系。

爆发重叠率属于解释指标，不应成为未经验证的强制目标。有时多使用一次饰品与等待爆发对齐之间存在取舍，交由相同场景下的总体结果评估。

## 9. 参考基线、对照组与评分

### 9.1 必须建立的对照

| 标识 | 名称 | 用途 |
|---|---|---|
| `B_std` | Standard APL（标准动作列表基线） | 描述与上游标准玩法模型的差距；不是严格数学上限 |
| `S_seed` | Seed Sequence（初始合法序列） | 衡量搜索本身是否带来改善 |
| `S_best` | Best Found Sequence（已发现最佳序列） | 本次搜索结果，必须独立复测 |
| `B_policy` | Policy-matched Reference（相同动作约束参考） | 存在动作排除或手动策略时，辅助解释差异来源 |

第一版至少实现前三项。`B_policy` 如未实现，应显示“未提供”，而不是把标准列表改个标题冒充它。辅助模式发布前必须实现相应的约束一致性比较。

### 9.2 比较条件

角色、装备、物品效果、场景、增益、消耗品、初始资源、战前操作和版本必须一致；差异只来自明确声明的控制方式。标准 APL 与 GSE 的输入控制差异本身是研究对象，不得隐瞒。

若序列排除了标准 APL 会使用的动作，相对标准基线的差距会混合“动作范围差异”和“序列决策差异”。报告必须列出这些排除项，并主要使用与合法初始序列的比较评估搜索效果。

### 9.3 指标定义

```text
相对标准基线：
eta_std = mean_DPS(S_best) / mean_DPS(B_std)

相对初始序列改善：
gain_seed = mean_DPS(S_best) / mean_DPS(S_seed) - 1

相同动作约束下的比例（实现该参考时）：
eta_policy = mean_DPS(S_best) / mean_DPS(B_policy)
```

DPS（每秒伤害）的均值必须来自规定的重复模拟。若分母无效、为零或结果不完整，比例为空并报告原因。

超过标准基线的 100% 不自动视为错误，也不自动宣称突破理论极限；先检查动作范围、样本误差、参考列表与版本一致性。[S08]

### 9.4 排名方式

采用“约束优先、输出为主、复杂度作近似平局裁决”的规则：

1. 先剔除不合法、不可导出、模拟无效或未满足支持条件的候选。
2. 在同一任务条件下，以重复模拟的期望输出作为主目标。
3. 对表现接近且差异未被可靠证实的候选，优先保留较短、对节奏扰动更稳定的序列。

可把相对差距 0.5% 设为初始复杂度容忍区间，但它是可调产品参数，不是已证实的自然阈值。比较不充分时应增加样本，或明确标为近似平局。

**不使用“DPS 减去总空按率”的简单评分。** 公共冷却中的正常尝试、非公共冷却饰品失败与真正可避免的技能空闲，成本不同。

### 9.5 诊断指标

| 指标 | 解释边界 |
|---|---|
| 无前台技能执行的输入占比 | 仅描述输入利用情况，不直接等于输出损失 |
| 可避免的动作空闲时间 | 需要明确可行动作和排队语义，不能简单用总公共冷却空隙代替 |
| 资源溢出 | 由引擎记录实际溢出，而非根据施法频率估算 |
| 关键动作执行次数 | 区分主动施放、额外触发与周期伤害 |
| 饰品使用次数和延迟 | 区分资源/施法限制、共享冷却和序列触达延迟 |
| 输入扰动敏感性 | 体现候选是否依赖不现实的固定节奏 |
| 序列长度 | 统计编译后有效动作块数，而非仅源代码行数 |

## 10. 搜索算法

### 10.1 第一版使用多起点局部搜索

采用 **Multi-start Local Search（多起点局部搜索）**，配合候选淘汰和少量随机重启。先实现可调试、可复现的算法，不把完整遗传算法作为前置依赖。

初始候选来自：统一可按动作集合的均匀合法排列、基线成功主动执行的频率统计、少量简单重复模板及随机变体。技能、已装备主动饰品和未来支持的药水使用同一动作表示；被动效果留给原生引擎，首版药水关闭。可按动作出现次数是尝试频率，不是成功执行次数；动作与物理按键不要求一一对应，同块命令顺序与分组必须在模拟和导出中一致。

从模拟结果统计动作时，不能把周期伤害、宠物自动攻击或被动触发当成玩家按键。模拟器的样例施法轨迹仅用于提供搜索起点，不是待逐字重放的最优答案。

### 10.2 变异操作

| 操作 | 修改对象 |
|---|---|
| 交换 | 交换两个动作块的位置 |
| 替换 | 替换块中的一个允许主动动作 |
| 插入/删除 | 调整动作频率及序列长度 |
| 片段移动 | 改变短片段的位置，保留内部次序 |
| 块内调整 | 在已支持的块结构中统一增删、移动动作；技能与主动使用物品遵守同一套合法性检查 |
| 随机重启 | 避免所有候选收敛到同一个局部区域 |

每次变异后立即做结构、长度、动作支持条件和导出合法性检查，不能先花大量计算评估无效程序。战斗中的暂时冷却或资源不足交给引擎判断，不能据此永久排除动作。依据资源溢出、动作长时间未被尝试等轨迹线索提出修改，同时保留随机探索；线索不代替实际输出评分。

### 10.3 分级评估

| 阶段 | 初始工程设置 | 目的 |
|---|---|---|
| 冒烟 | 每个新能力仅少量迭代，保留完整轨迹 | 发现错误，不用于排名 |
| 粗筛 | 每个候选约 200 次迭代 | 淘汰明显较差的候选 |
| 精筛 | 入围候选约 2,000 次迭代，使用不同种子集合 | 降低选择噪声 |
| 最终复测 | 锁定候选后，用独立的 20 个种子批次，每批约 500 次迭代 | 估计表现与区间 |

上表数字仅为原始方案示例，不是已确定的运行参数。用户确认采用分批加测：明显落后的候选停止追加，有竞争力或难分胜负的候选获得更多独立样本；不按噪声排名机械淘汰。完整战斗时长保持一致，降低成本靠减少重复次数，不缩短战斗偏向爆发。预算由计算预算票依据 P2 测量确定；区间仍过宽时增加样本，预算不足则显示“证据不足”。最终独立复测预算须预留，未完成复测不得称已验证。

同一编译结果与完整任务条件下复用已完成样本，加测仅补未使用批次，按实际有效样本数汇总，不重复计数。优先验证原生 ProfileSets（配置批量模拟）的兼容性后再使用；当前控制器尚未通过该能力验证。搜索主要保存摘要，轨迹按需采集；具体并发数与运行开销交给计算预算票，不预先承诺加速比例。

### 10.4 搜索流程

```text
解析角色并检查能力。
建立标准基线及简单合法初始序列。
生成多个合法起点。
循环直到预算用完或触发停止条件：
    从当前保留集合生成候选。
    编译为统一的动作块序列。
    依据完整任务键查询缓存。
    对未评估候选进行粗筛。
    对可能改善的候选增加独立样本。
    更新候选档案，保留稳定且有竞争力的解。
    保存搜索状态与随机数状态。
锁定一个待发布候选。
用未参与选优的复测集评估该候选及所有必要基线。
生成报告，执行导出往返与一致性校验。
```

停止条件包括候选预算、用户取消和多轮无可信改善。不使用“达到 95% 就视为成功”作为固定终止规则。

每次运行前固定预算、无改善判据及检查轮次，不能看结果临时改停止标准。无改善停止只表示本次预算和搜索范围内未发现可信提升，不证明全局最优。时间耗尽或取消时保留完整结果，未完成复测则报告证据不足；具体限额和取消恢复机制由计算预算票确定。

### 10.5 不应做的优化

不能给每个候选重新选择更有利的角色装备、输入频率、战斗时长或手动策略。若这些也要搜索，必须作为显式任务并在共同测试分布上比较。

去重只合并真正相同的编译结果与条件。循环序列的旋转可能改变开场，不能无条件视为等价。重新启动模拟、改变线程数或改变数据库后，也不能误命中旧结果。

## 11. 统计验证、节奏稳定性与个性化收益

### 11.1 三套数据必须分开

| 集合 | 允许用途 | 禁止用途 |
|---|---|---|
| 搜索集 | 生成和修改候选 | 作为唯一最终成绩 |
| 验证集 | 选择入围候选与调整搜索配置 | 与最终复测集混用 |
| 最终复测集 | 锁定候选后的最终比较 | 看过结果再反复改候选仍称独立测试 |

至少分离搜索随机数、战斗随机数与输入扰动随机数。SimulationCraft 的固定种子与线程有关，应锁定线程布局并记录种子。[S07]

相同种子不代表不同序列会获得逐次相同的暴击或特效结果，因为动作改变可能改变随机数消耗顺序。可以使用共同种子批次进行配对比较，但不能宣称完全消除了随机性。

### 11.2 报告不确定性

对每批独立模拟计算均值，再报告候选与基线差异的 95% 置信区间。实现可采用对独立批次的配对重采样；保存批次数、单批迭代数、计算方法和原始摘要。

若差异区间跨过零，标注“尚未证实优于对照”。若模型一致性测试未通过，即使统计区间很窄，也不能标注结果可靠。

### 11.3 节奏鲁棒性

对最终候选至少测试：名义间隔、间隔小幅扰动、较慢输入以及短暂停顿后的恢复。幅度由用户输入模型与实际测试确定，示例设置不得伪装成已测得的用户习惯。

当前名义间隔为 300 毫秒。扰动分布、较慢间隔、暂停时点与持续时间须在查看最终复测结果前写入运行清单；同一情景下候选与对照使用一致的输入生成规则和配对批次。分别报告各情景均值、相对差异区间及退化，不事后挑有利情景。验证集可辅助选优；最终复测及最终扰动结果只能用于报告，若据此修改候选，必须另建未使用的最终复测集。

固定输入周期可能与序列长度、公共冷却形成偶然对齐。特别高的固定节奏成绩必须通过相位和节奏扰动检查，不接受仅在一个精确毫秒值上优秀的“最优解”。

### 11.4 统一动作搜索的必要对照与可选诊断

必须比较相同角色、装备和场景下的标准原生基线、简单合法初始序列与本次最佳候选。标准原生基线用于展示序列约束下的差距，搜索是否改善首先与同样按键约束的初始序列比较；不得把自由选招基线直接当成可导出的回退序列。

技能与主动使用物品共用搜索算法，不要求分别实施“仅技能”和“仅饰品”优化。有必要解释改善来源时，可以冻结部分动作位置作诊断对照；这是可选实验，不是首版必跑的两套优化流程。比较不同角色时，各自对照其本身的基线，不比较裸输出大小。

随后用少量代表性配置交叉测试，包括双被动、单主动、双主动以及不同急速状态。目的在于量化个人优化收益与缓存复用范围，**不是把已经确定的个人工具改回毕业模板数据库**。

## 12. GSE 字符串导出

### 12.1 当前源码提供的线索

本次核查的 GSE 主分支中，普通编码路径使用以下组合：[S09]

```text
GSE 对象
  → CBOR（紧凑二进制对象表示）序列化
  → 压缩
  → Base64（二进制转文本编码）
  → 添加 !GSE3! 前缀
```

客户端生成接口文档显示压缩默认方法为 Deflate（无损压缩方法），文本编码默认采用标准变体；这些资料来自客户端接口文档的公共源码镜像，而非暴雪托管的网站。[S11]

**仍需验证二进制封装、表结构和目标发布版差异。** 不能仅按算法名称随意选择压缩头、数组编码或元数据字段，然后宣布兼容。

### 12.2 编码适配器要求

| 项目 | 要求 |
|---|---|
| 版本分派 | 按目标发布版本选择适配器，不把当前主分支当成通用格式 |
| 外层对象 | 从实际 GSE 导出样本与导入路径确定，不只生成内层动作列表 |
| 表类型 | 保留数组、整数键、字符串键、空表等语义，不把所有表都转成普通 JSON 对象 |
| 元数据 | 根据目标导入器填写序列名称、专精、版本和必要元数据 |
| 技能映射 | 使用已验证的基础法术与本地化路径，不能直接输出未解析的英文动作标记 |
| 压缩与编码 | 用真实样本验证封装、前缀、字符集及填充规则 |
| 校验字段 | 以目标版本实际要求为准，不能编造校验和占位值 |
| 外部宏/变量 | 第一版不依赖，确保导入到干净配置也能运行 |
| 受保护内容 | 不处理受保护、禁止导出的第三方序列；只导出本项目生成的普通内容 |

主分支存储代码和序列化代码仅作为适配入口，最终契约须从锁定版本提取。[S09]、[S10]

### 12.3 往返验证

必须具备以下证据：

```text
游戏内 GSE 创建最小测试序列 → 导出真实字符串
    → 外部工具解码 → 与预期结构一致

外部工具创建同等结构 → 编码
    → 游戏内 GSE 导入成功 → 查看编译结果和实际按键行为

导入后的序列再次导出
    → 外部工具解码 → 核心结构与动作顺序一致
```

不要求两次字符串逐字相同，因为压缩方式、元数据或键顺序可能改变；要求对象关键语义和编译执行序列一致。

至少覆盖中文说明、重复技能、槽位 13/14、多命令动作块、错误输入、超长输入和当前专精法术替换。

### 12.4 状态分层

| 状态 | 含义 |
|---|---|
| 编码自测通过 | 本地编码与解码能往返，仅是最低层检查 |
| 目标 GSE 导入通过 | 用户实际版本可接受文本 |
| 编译结构通过 | 目标版本编译出的命令序列与被模拟序列一致 |
| 游戏行为校验通过 | 已完成规定的手动按键与日志对照 |

只通过第一项，不能在报告写“已验证可用”。没有游戏客户端时，Codex 应交付可执行的人工检查步骤并标记待验证，不得伪造测试结果。

## 13. 手动辅助模式的后续设计

辅助模式不属于第一版阻塞项，但数据结构应允许未来增加。

| 要求 | 实现约束 |
|---|---|
| 明确手动技能集合 | 例如灵界打击、打断、防御或主动饰品，由用户选择 |
| 明确输入模型 | 使用固定时间表、录入的输入轨迹，或明确标注的模拟玩家策略 |
| 共享角色状态 | 手动动作与 GSE 消耗同一份符文、符能、冷却和输入机会 |
| 输入仲裁 | 同一时刻的手动技能与序列输入必须有确定优先顺序，不能同时免费获得两个公共冷却动作 |
| 基线公平 | 对照与候选使用同一种手动策略、反应延迟和输入预算 |
| 无策略不评分 | 用户标为手动却没有有效模型时，拒绝输出完整效率 |
| 解释范围 | 即使使用模拟玩家策略，也只是该策略条件下的表现，不代表真实玩家必然做到 |

血 DK 生存目标必须作为独立研究范围：需要有可信的承伤、治疗与防御评价模型后才能加入。不能从输出最大化顺手推导“最安全的灵界打击时机”。

## 14. 命令行、配置与后端协议

### 14.1 命令行接口

任务 11 用户评审明确：日常用户界面只保留“粘贴角色字符串并开始 → 展示流程和进度 → 复制导入字符串”。首版无药剂选项；未来支持后再增加是否使用选项。诊断、验证、资源配置与取消恢复等内部能力不作为日常页面的操作清单，开发者通过下列命令或内部工具验证；发生错误时只显示简短原因与下一步。各层验证仍须真实记录，不合并为虚假的成功，也不要求用户逐项审阅技术细节。

**本节所有 `sim2gse` 命令均为本项目待实现接口，不是已经发布的工具或 SimulationCraft 原生命令。**

| 命令 | 用途 |
|---|---|
| `doctor`（环境诊断） | 检查引擎、补丁协议、版本锁定和编码适配器 |
| `inspect`（配置检查） | 显示角色、天赋、装备、主动饰品和不支持项 |
| `baseline`（参考模拟） | 建立标准 APL 与简单合法序列对照 |
| `simulate`（序列模拟） | 只评估一个指定的项目序列，便于调试 |
| `optimize`（序列优化） | 完整个性化搜索与最终复测 |
| `validate`（结果复测） | 对已有候选使用新的种子和输入扰动集合 |
| `export`（结果导出） | 编码已通过必要检查的候选并保存导入文本 |
| `resume`（恢复任务） | 按原始清单和预算恢复未完成任务 |
| `panel`（交互面板） | 引导导入、检查和运行，不另实现一套业务逻辑 |

PowerShell（命令行环境）形式的预期操作：

```powershell
sim2gse doctor --config ".\project.toml"
sim2gse inspect ".\character.simc" --config ".\project.toml"
sim2gse optimize ".\character.simc" --config ".\project.toml"
sim2gse resume ".\runs\run-001"
sim2gse export ".\runs\run-001" --output ".\best.gse.txt"
```

上述路径是示例。命令实现后，所有入口都必须提供中文帮助，并支持机器可读结果或退出码，便于脚本调用。

### 14.2 示例任务配置

下列为项目配置示例。**单目标和 300 毫秒名义间隔已由用户选定；该间隔尚未实测校准，扰动及其余数值仍为工程初值。版本锁文件必须由 P0 与环境诊断生成，不能用占位内容运行正式任务。**

### 14.3 后端协议

Python 侧通过受控子进程调用原生引擎，不嵌入整套引擎。原生 `json2` 报告可作为基础结果来源；新增诊断字段使用独立版本化输出。[S06]

建议新增以下**项目补丁接口**，名称可在 P0 调整，但一经发布须版本化：

| 拟新增接口 | 作用 |
|---|---|
| `sim2gse_info=1` | 返回后端协议版本、上游提交、补丁版本与能力 |
| `sim2gse_input=<path>` | 加载受控的序列、输入模型与策略描述文件 |
| `sim2gse_metrics=<path>` | 保存扩展统计与验证摘要 |

这些参数在未打补丁的 SimulationCraft 中不存在。`doctor` 必须识别原版引擎与扩展引擎，不能把“不识别参数”降级为普通模拟后继续输出成绩。

请求至少包含：协议版本、角色哈希、场景、动作策略、序列中间表示、输入模型、种子、迭代数和输出位置。响应至少包含：运行状态、版本清单、均值与样本信息、动作统计、错误列表和产物路径。

使用参数数组与 `shell=False` 调用可执行文件；在任务专用目录中运行，显式处理超时、取消与子进程退出，禁止把角色输入直接拼接为命令行脚本。[S18]

## 15. 分阶段实施计划

### 15.1 阶段与交付物

| 阶段 | 必须完成的工作 | 交付物 | 进入下一阶段的条件 |
|---|---|---|---|
| P0：兼容性与可行性 | 锁定引擎/GSE/游戏版本；检查用户邪恶死亡骑士样本、等级、天赋和饰品；运行单目标原生基线；核实编码协议与动作调度入口 | 兼容性报告、版本锁、真实或明确标注的测试配置、原生报告、风险清单 | 目标角色可正常模拟；明确可支持子集；不存在被忽略的关键物品效果 |
| P1：序列与导出闭环 | 实现中间表示、合法性检查、目标版本编码适配器；完成最小序列真实导入和编译对照 | 序列格式、编码测试样本、导入文本、人工验证记录 | 工具生成的序列能在目标 GSE 中导入，编译出的动作与预期一致 |
| P2：可信执行模型 | 增加按键事件控制器、队列适配、饰品组合、日志；关闭隐藏主动扫描；完成回归与游戏对照 | 扩展引擎、单序列模拟命令、语义测试集、模型一致性报告 | 不再把普通 APL 当 GSE；关键输入/队列/饰品用例通过；补丁关闭无异常回归 |
| P3：个性化搜索 | 实现初始候选、多起点搜索、分级评估、缓存与独立复测；完成饰品消融对照 | 优化命令、候选档案、真实结果报告、可复现运行目录 | 能在同一个可信模型中比较候选；最终成绩有独立复测证据 |
| P4：终端产品化 | 中文向导、进度面板、诊断、恢复、错误处理、打包和说明书 | Windows 运行包、用户说明、兼容性清单、回归报告 | 在干净环境完成输入 → 优化 → 导出 → GSE 导入全链路 |
| P5：扩展 | 固定多目标、手动辅助模式、多场景分布、更多专精、复杂饰品及经过验证的高级块 | 各能力独立的测试与支持清单 | 按能力逐项发布，不回退既有执行准确性 |

### 15.2 P0 的具体任务

| 编号 | 任务 | 验收证据 |
|---|---|---|
| P0-01 | 获取与目标游戏对应的上游代码，记录固定提交和数据构建号 | 版本锁文件，能够重新定位到相同源码 |
| P0-02 | 构建或取得同提交的原生引擎，运行用户提供的有效邪恶死亡骑士配置 | 真正的退出码、原生输出和报告文件 |
| P0-03 | 审查当前角色天赋与饰品的模型覆盖 | 已支持、需验证、不支持三类明细 |
| P0-04 | 跟踪角色动作就绪、非公共冷却、排队与执行调用链 | 简明源码路径说明，不要求复制大段上游代码 |
| P0-05 | 收集目标 GSE 的最小序列导出样本并确定编码格式 | 样本、解码结构与版本关联 |
| P0-06 | 定义第一版支持子集和测试预期 | `compatibility.md` 与初始语义测试表 |

用户已提供邪恶死亡骑士样本，当前进度以[实施地图](../myspec/changes/sim2gse-wayfinder/spec.md)为准，严格按地图顺序推进。提前产生的[原生运行材料](sim2gse/target-evidence.md)仅供将来复核，不计为后续任务完成。先得到离线候选模拟结果，到真实导入验证阶段再讨论插件安装与实际配置；本文其它要求若将安装提前作为离线工作的前置，以此用户决议为准。必要的通用测试使用明确标注的测试配置，不以历史鲜血角色替代本次目标；待游戏验证不能填成通过。

### 15.3 P1—P2 的最小纵向闭环

不要先实现几千种候选搜索。依次完成：

```text
一个合法技能动作块
    → 本地编码
    → GSE 导入并验证
    → 引擎中按输入流执行

两个技能动作块，包含不可用的步骤
    → 验证失败步进与公共冷却期间的输入

一个非公共冷却主动饰品 + 一个技能
    → 验证同块顺序与真正执行时间

两个主动饰品 + 技能
    → 验证共享使用限制、顺序、失败与后续技能

完整但固定的角色研究序列
    → 得到可信、可复现的动作统计与输出
```

只有这些用例成立，P3 的搜索成绩才有意义。技术上能让模拟器“输出一个数字”，不属于 P2 完成。

### 15.4 阶段结束报告

每阶段提交简短记录，包含已实现内容、实际执行的测试、未执行测试及原因、已知限制、相关产物路径和下一阶段的前置条件。不得把界面截图、模拟假数据或本地编码自测代替端到端证据。

## 16. 测试计划与通过标准

### 16.1 自动化测试矩阵

| 编号 | 测试 | 必须确认的性质 |
|---|---|---|
| T01 | 角色导入 | 中文、注释、背包装备不改变当前装备身份 |
| T02 | 输入安全 | 非法外部文件引用、输出路径及额外执行指令被拒绝 |
| T03 | 能力检查 | 未学会技能、错误天赋、未知物品效果不进入有效搜索 |
| T04 | 单技能循环 | 输入数、尝试数、排队数、执行数分别正确 |
| T05 | A → B → C 中 B 不可用 | 下一次输入推进，不在同次输入中按 APL 自动选 C |
| T06 | 公共冷却期间连按 | 序列步进及队列行为符合选定语义 |
| T07 | 队列覆盖 | 新输入、旧队列和最终执行可追溯，不出现幽灵施法 |
| T08 | 饰品与技能同块 | 非公共冷却饰品不被一律当成独立公共冷却步骤 |
| T09 | 双主动共享限制 | 改变 13/14 顺序后，实际使用与拒绝原因正确 |
| T10 | 施法或引导中输入 | 不越过原生施法限制；未支持方式明确报错 |
| T11 | 关闭控制器 | 与相同上游提交的原版引擎无非预期变化 |
| T12 | 隐藏动作扫描 | 被排除的主动技能不会由原生 APL 或物品扫描补放 |
| T13 | 法术替换 | 基础技能、天赋替换与日志中的执行动作正确对应 |
| T14 | 结构往返 | 编码/解码保留动作、顺序、槽位及必要元数据 |
| T15 | 编译一致性 | 导出后实际编译的序列与被模拟序列一致 |
| T16 | 重置与起始相位 | 改变起始位置、脱战规则不会错误复用缓存 |
| T17 | 随机数与线程 | 相同清单可复现；改变相关条件触发缓存失效 |
| T18 | 失败与取消 | 中断进程不产生“成功”结果；恢复不重复计算已完成任务 |
| T19 | 搜索退化 | 找不到更优解时保留有效对照并报告无显著改善 |
| T20 | 统计隔离 | 最终复测集没有被用于候选选择 |
| T21 | 不合法手动模式 | 严格模式不接受没有控制器的手动技能或饰品 |
| T22 | 发布环境 | 中文路径、空格路径、无管理员权限和缺失依赖都有明确行为 |

确定性测试使用简化测试角色或测试动作验证事件机制，但这些测试专用伤害模型不能用来产生真实角色的成绩。

### 16.2 游戏内人工验证

使用现有 GSE 的编辑、调试功能及当前客户端可用的日志，不开发额外游戏插件。

| 步骤 | 记录 |
|---|---|
| 固定版本、天赋、装备、增益和目标环境 | 构建号、角色导出与 GSE 配置 |
| 导入最小测试序列 | 导入成功、名称、专精、实际编译结构 |
| 测试单步与不可用技能 | 手动按键次数、步骤变化及成功施法 |
| 测试同块饰品与技能 | 调用顺序、饰品成功时刻、技能是否成功或排队 |
| 测试双主动顺序 | 实际先使用者、另一饰品可用时刻和再次使用情况 |
| 测试不同输入节奏 | 输入条件、队列差异和恢复行为 |
| 对照后端轨迹 | 首先检查动作行为，再讨论输出误差 |

战斗日志通常不能完整代表每一次失败输入。缺少输入或失败证据时，不能从成功施法日志反推所有步骤都正确；应使用当前版本可用的调试信息或将相应用例标记为证据不足。

### 16.3 发布判定

所有确定性执行语义用例必须通过。随机战斗结果应比较动作分布、使用时间与多次实测范围，而不是要求单次游戏木桩输出和模拟器完全相等。

模型与游戏差异超过已定义的测试容忍度时，应阻止该能力被标为“已验证”。不能为了让结果通过，针对每个候选单独修改校准参数。

## 17. 性能、缓存与断点恢复

用户已确认的首版试行细则以[计算预算、缓存与恢复契约](sim2gse/runtime-contract.md)为准：总上限 10 分钟、最多双进程各单线程、搜索最迟第 7 分钟结束、立即取消并保存完整结果；该文还规定分批预算、最终复测情景、缓存身份及恢复门槛。下文为通用要求，旧示例不是覆盖该决议的默认值。

### 17.1 先测量，再提高搜索预算

扩展模型会新增大量输入事件。例如 180 秒战斗、300 毫秒间隔，在没有停顿时约有 600 个输入事件；乘以候选数和迭代数后，事件数量很快增大。这只是事件数量计算，不是运行时间预测。

P2 记录原生基线、单序列模型及完整日志模式的实际吞吐量。P3 根据本机测量结果选择预算，界面展示已完成候选与实际耗时，不声称某个固定硬件之外的保证速度。

### 17.2 并行策略

| 项目 | 要求 |
|---|---|
| 默认调度 | 外层候选并行，内层每个引擎少量线程 |
| 资源上限 | 外层并行数 × 内层线程数不得无控制地超过用户预算 |
| 基线与复测 | 固定线程布局，保持可复现性 |
| 工作目录 | 每个任务和子任务使用独立路径，避免报告文件相互覆盖 |
| 日志 | 搜索与最终复测保存完整统计摘要及身份；详细轨迹仅针对受限诊断样本，不记录所有重复战斗的完整按键 |
| 界面 | 显示基于真实任务事件的进度，不根据代数编造输出提升 |

### 17.3 缓存键

缓存键至少包含：规范化角色、实际装备与特效、上游与补丁版本、数据版本、动作策略、编译序列、输入模型、重置规则、场景、随机种子、迭代数及线程布局。

只有不影响语义的展示性字段可以排除，例如用户自行添加的备注。不能通过随意排序原始配置或宏命令来“规范化”而改变执行含义。

### 17.4 恢复规则

持久化搜索随机数状态、候选档案、已完成任务、待执行队列、预算和版本清单。采用原子写入与数据库事务，只有结果完整且校验通过的任务才能标记完成。

恢复时遇到版本、配置或模型变化，应创建新任务或明确拒绝原地续跑。不要把新旧模型的候选成绩混在一个排行榜。

## 18. 错误处理与可信输出

| 错误 | 必须采取的行为 |
|---|---|
| 原生引擎不支持目标角色或物品 | 列出具体缺失，停止相应优化 |
| 传入原版而非扩展引擎 | 诊断失败，不自动回退为普通 APL 模拟 |
| 序列含不支持结构 | 在评估前拒绝，给出动作块和命令位置 |
| 引擎进程失败或报告损坏 | 保留日志并标记失败，不把输出设成 0 作为正常样本 |
| 部分候选失败 | 不进入有效排名；汇总失败原因供修复 |
| 最终独立复测未完成 | 可以保存中间候选，但不能显示最终已验证成绩 |
| 不能编码为目标版本 | 可以保存研究结果，不生成假导入字符串 |
| 本地编码通过、游戏导入未验证 | 明确区分两种状态 |
| 未找到可信改善 | 输出有效候选和“未证实改善”，不虚构小数位收益 |

建议退出码：成功为 0，配置错误为 2，兼容性不通过为 3，引擎失败为 4，验证未完成为 5，用户取消为 130。具体值属于项目协议，应在测试和帮助中保持一致。

## 20. 本地运行、发布与维护

### 20.1 隐私与运行边界

角色资料和报告默认保存在本机，不自动上传。分享报告时提供移除角色名、服务器名及原始导出的选项。

工具不写入游戏目录，不修改正在运行游戏的配置，不接管键盘，不监视游戏进程。用户在游戏内自行导入与按键。首次读取剪贴板如被实现，也只能由用户显式操作触发，不进行持续监听。

### 20.2 发布要求

Windows 运行包应包含前端、对应引擎、版本清单、依赖与数据准备说明，以及第三方许可材料。开发时审查上游和依赖的实际许可证，确定代码、数据及补丁的可分发范围；不能因为仓库公开可见就默认可以任意再分发。

不要求终端用户安装 C++ 编译环境。开发构建脚本必须固定上游提交与依赖，并能在干净构建环境生成同一套受测组件。

### 20.3 版本升级

| 变化 | 需要重做的检查 |
|---|---|
| 游戏或职业平衡改动 | 数据、动作映射、效果覆盖与代表性配置回归 |
| GSE 发布更新 | 编码、元数据、动作块编译与绑定行为 |
| 模拟器更新 | 补丁调用链、基线回归、装备与动作模型 |
| 编码库更新 | 真实样本往返与目标客户端导入 |
| 输入模型修改 | 语义测试、稳定性测试与相关缓存失效 |

每份已发布序列都附适配条件。角色换装备、换天赋、换饰品槽位或改变输入方式后，可以重新运行；工具不能在未重新评估时保证旧序列仍最佳。

## 21. 第一版完成定义

下表全部满足，才算完成最小可行版本，而不是仅完成演示界面。

| 验收项 | 完成标准 |
|---|---|
| 角色级输入 | 能处理用户提供的真实且受支持的邪恶死亡骑士 `/simc` 配置，在单目标下运行并正确识别两件饰品 |
| 无新增插件 | 整套产品不要求安装专用魔兽插件 |
| 原生计算 | 基线与候选均有真实 SimulationCraft 运行记录 |
| 执行可信 | 已通过公共冷却、失败步进、队列、同块饰品与双主动相关用例 |
