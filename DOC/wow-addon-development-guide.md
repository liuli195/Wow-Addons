# 魔兽插件开发与人工智能协作指南

版本：人工智能主导开发版。资料与本机技能核查日期：2026-09-07。当前仅考虑 Windows（视窗系统）与魔兽 12.1 正式服；不纳入怀旧服、测试服和其他补丁版本。接口资料进一步锁定到实际客户端构建号。

**目标：人工智能无需启动编辑器，就能调查源码、实施改动、运行检查、读取诊断、准备游戏验收，并通过 GitHub（代码托管平台）的 PR（拉取请求）完成交付。**

流程主线：

**需求和验收 → 固定基线与功能分支 → 核实接口 → 小步实现 → 本机快速验证 → 游戏验收 → 提交与推送 → 远端完整验证和审查 → 合并 → 清理 → 按需发布安装包。**

本指南描述方案与工作约定，实际落地环境见[环境使用说明](environment-setup.md)。前期工具能力和社区采用证据见[研究笔记](wow-addon-debug-testing.md)。本指南中的技能限制以本次读取的本机 2.0.0 版技能为依据；升级后重新读取技能，不照抄旧参数。

## 1. 本仓库现状与第一期范围

初始化前核实的基线（部署后的状态以环境使用说明和实际配置为准）：

- 这是自制插件、素材、代码片段和第三方插件混合保存的仓库，没有必要整体搬家。
- 自制插件位于 AddOns/EUI_FacetedPortrait，依赖 EllesmereUI（界面插件）及其单位框体模块。
- scripts/media/verify.py（素材验证脚本）已实测通过，覆盖 13 个素材及部分代码约束；这不代表游戏内显示已经验收。
- scripts/snippets/（个人脚本目录）包含依赖不同运行环境的片段，不能一概当成可独立加载的插件或现成测试。
- 本机 build-and-verify（构建与验证命令）可以调用；gh（GitHub 命令行工具）可以调用；已安装 PR Flow（拉取请求流程）技能，其脚本帮助入口可运行。
- 本仓库尚无 .build-and-verify/config.json（构建与验证配置）、.pr-flow/config.yaml（拉取请求配置）和远程地址，不能直接声称已具备远端交付能力。
- 先前定向检查没有在当前命令环境发现独立 Lua（脚本解释器）、Luacheck（静态检查器）或编辑器命令。安装前再检查；这不等于整台机器不存在其他安装。

第一期覆盖自制插件与现有素材验证。AzeriteUI（第三方界面插件）、本地整合包、配置收藏不作为自有代码质量门禁；代码片段逐项识别运行环境后再纳入。素材生成所需源图缺失时不运行生成器。

没有测试用例时如实报告“尚无运行测试”，不能把空测试目录或空检查当作通过。

## 2. 人工智能开发环境：命令行优先

### 2.1 工具职责

| 工具 | 面向人工智能的职责 | 配置优先级 |
| --- | --- | --- |
| Git（版本管理） | 差异、固定基线、分支、提交、回退 | 必需 |
| gh（GitHub 命令行工具） | 读取认证、仓库、拉取请求和检查结果 | 接入远端时必需 |
| Build and Verify（构建与验证） | 唯一常规构建与验证总入口 | 必需 |
| PR Flow（拉取请求流程） | 诊断、收尾、审查门禁、合并和安全清理 | 远端交付必需 |
| LuaLS（Lua 语言服务器）独立程序 | 游戏接口、参数和类型诊断，输出报告 | 基础检查 |
| 魔兽接口定义文件 | 为独立语言服务器描述真实游戏环境 | 与语言服务器一同配置 |
| Luacheck（静态检查器） | 语法、未定义变量和代码问题检查 | 基础检查 |
| Lua 5.1（脚本解释器） | 执行隔离后的真实逻辑，必要时提供少量游戏接口替身 | 有运行测试时必需 |
| Python（解释器）及现有素材依赖 | 复用素材验证，执行必要的小工具 | 本仓库已有需求 |
| WoW UI Simulator（魔兽界面模拟器） | 游戏外加载、控件检查、截图及回归测试 | 兼容性试验后按需加入 |
| VS Code（代码编辑器）及扩展 | 方便人查看、修改代码 | 可选，不是人工智能前置依赖 |

Ketho WoW API（魔兽接口提示）的编辑器扩展不是独立命令行环境。人工智能需要的是其接口注解等定义材料，被独立 LuaLS 正确加载。成熟项目 DBM（首领战插件）也分别提供编辑器配置和命令行检查配置，但其中 DBM 专属诊断不应直接用于普通插件。[Ketho 作者仓库](https://github.com/Ketho/vscode-wow-api)、[DBM 独立检查说明](https://github.com/DeadlyBossMods/LuaLS-Config)

### 2.2 工具版本和获取方式

安装前清点已有工具；能复用就复用。项目记录工具版本、来源、接口定义提交、校验摘要和调用方式。只维护一个版本记录来源，远端安装读取它，避免本机与远端各写一套版本。

可采用被忽略的 .tools/（工具缓存目录）保存便携工具和定义文件；版本记录保存在可提交的小文件或项目说明中。缓存、可执行文件、诊断报告和个人游戏路径不进入源码提交。已有工具锁定机制时复用，不预建大型安装框架。

Luacheck 作者提供 Windows 单文件程序，能减少 LuaRocks（Lua 包管理器）前置安装。程序自身打包的 Lua 版本与受检代码版本不同；使用 lua51（5.1 标准环境）检查，并不意味着程序是可用于游戏外测试的 Lua 5.1 解释器。[安装说明](https://github.com/lunarmodules/luacheck#installation)

独立 Lua 测试解释器使用可信来源；若无合适的受维护分发，评估从官方源代码构建的成本，不能下载来历不明的程序。解释器安装方式确定后记录，不在指南中猜测包管理器标识。

验收工具时，成功启动只是第一步，还必须验证失败行为能被上层识别。

### 2.3 独立语言服务器与游戏接口

实施顺序：

1. 下载并固定 LuaLS 独立发行版。
2. 获取与目标客户端相匹配的接口定义，固定其提交或版本。
3. 检查实际目录结构，确认注解、生成文件或子模块是否齐全，不假定克隆仓库后就一定可用。
4. 在 .luarc.json（语言检查配置）中设置 Lua 5.1、外部定义路径和自有源码范围。
5. 核实所用第三方依赖接口，必要时补少量真实类型声明，不伪造全功能实现。
6. 运行一份正确代码、一份错误全局变量样例，以及一份注解确实覆盖的错误参数样例，验证报告与退出行为。

示意配置如下；YourAddon（你的插件）和库目录只是占位名称，落地时必须替换为实际存在的路径：

~~~json
{
  "runtime.version": "Lua 5.1",
  "completion.autoRequire": false,
  "workspace.library": [
    ".tools/wow-api/Annotations/Core",
    ".tools/wow-api/Annotations/FrameXML"
  ]
}
~~~

这是结构示例，不是对任意版本注解目录的保证。.luarc.json 的键不带 Lua. 前缀；编辑器设置才使用该前缀。库路径须按实际检查工作区解析，从子目录检查时不能原样沿用根目录相对路径；必要时生成带绝对路径的本地配置，远端按自身检出位置生成。混合仓库应对单插件分别调用检查器或明确限制范围；外部定义可参与解析，但不将第三方源码全部作为自己的诊断对象。[LuaLS 配置](https://luals.github.io/wiki/settings/)

首次配置时可以直接探测底层命令；配置通过后，日常由 Build and Verify 调用。以下示例假定命令可发现且从项目根目录运行：

~~~powershell
$repoRoot = (Get-Location).Path
lua-language-server --check "$repoRoot/AddOns/EUI_FacetedPortrait" --configpath "$repoRoot/.luarc.json" --checklevel=Warning --check_format=json --logpath "$repoRoot/.local/luals"
~~~

报告位于指定日志目录的 check.json（诊断报告）。固定版本下实测“有问题时的退出状态”；若退出状态不足以执行项目门禁，只增加一个很薄的适配脚本，读取本次报告、输出文件与行号，并把达到约定严重级别的问题转为失败。报告缺失、生成失败或时间不匹配应报错，不能读取旧报告冒充新结果。[独立运行说明](https://luals.github.io/wiki/usage/)、[诊断报告说明](https://luals.github.io/wiki/diagnosis-report/)

### 2.4 正式服 12.1 接口定义和文档从哪里获取

**目前可取得覆盖广泛的资料组合，但没有核实到一份可保证“12.1 所有接口、完整类型和全部运行限制”的单一文件。** 暴雪生成文档、界面源码、运行环境清单和社区类型注解承担不同用途；类型检查通过也不保证战斗中允许调用。

本次直接读取上游版本文件及远端引用，确认以下可获取快照；它们不是对本机游戏版本的检测结果：

| 资料 | 本次核实结果 | 使用方式 |
| --- | --- | --- |
| Gethe/wow-ui-source（暴雪界面源码镜像） | 12.1.0 标签解析为 `8ea15b61e45c0ed4eba01439c90757f86eb78d34`；版本文件为 `12.1.0.69587` | 暴雪生成文档和真实界面调用的主要证据 |
| Ketho/BlizzardInterfaceResources（游戏接口资源清单） | 12.1.0 标签解析为 `36dd01db2d8fa5086dffda5cbfb3d55f4a70e526`；读取的说明记录构建号 69587、接口号 120100 | 查全局函数、事件、控件方法、模板、枚举等清单 |
| Ketho/vscode-wow-api（语言服务器接口注解） | 本次主分支提交为 `d0b5b51fac4c52c493371b9b18e66ce604ea4326`；更新记录仅明确写到 12.0.1 | 可作为注解候选，尚未确认完整匹配 12.1，不能直接作为版本基准 |

证据：[源码固定提交版本文件](https://github.com/Gethe/wow-ui-source/blob/8ea15b61e45c0ed4eba01439c90757f86eb78d34/version.txt)、[接口资源说明](https://github.com/Ketho/BlizzardInterfaceResources/tree/36dd01db2d8fa5086dffda5cbfb3d55f4a70e526)、[注解更新记录](https://github.com/Ketho/vscode-wow-api/blob/d0b5b51fac4c52c493371b9b18e66ce604ea4326/CHANGELOG.md)。网页搜索缓存可能落后于直接获取结果，因此版本判断以固定提交文件为准。

获取步骤：

1. 在目标正式服客户端执行 `/dump GetBuildInfo()`，记录版本、构建号、构建日期和接口号。当前已找到的快照为 12.1.0 / 69587 / 120100；只有客户端匹配时才采用该快照。12.1 的后续小补丁也不能自动混入。
2. 下载对应的界面源码快照，重点检索 `Interface/AddOns/Blizzard_APIDocumentationGenerated`（暴雪生成接口文档目录）。其中的 Lua（脚本语言）表描述函数参数、返回值、事件和数据结构，部分还包含受限参数规则。这是数据描述，不能直接当成语言服务器类型声明。
3. 保留同一份快照的其余界面源码，查模板、混入方法、加载顺序和暴雪实际调用。源码镜像包含不同客户端相关文件时，按正式服加载清单选择，不将全部文件视为正式服可用接口。
4. 下载匹配版本的接口资源清单，用 `GlobalAPI.lua`、`WidgetAPI.lua`、`ScriptObjectAPI.lua`、`Events.lua`、`Templates.lua` 等补查名称与覆盖范围。函数名清单本身不提供完整参数语义，也不能证明所有按需加载内容都已覆盖。
5. 获取注解候选，核对本插件使用的接口与暴雪 12.1 文档差异，再供 LuaLS（语言服务器）使用。缺失项可按证据补最少的项目注解；修正已有声明时避免重复定义。若需要系统性重新生成，遵循作者生成流程，并记录输入源码版本；不把生成器自己的 Lua 5.4 环境混作插件的 Lua 5.1 测试环境。

以下是获取命令示例，尚未执行。目录应为空或尚不存在；安装阶段先确认缓存目录的忽略规则。示例固定本次核实的源码提交，落地时须先核对客户端：

~~~powershell
git clone --filter=blob:none --no-checkout https://github.com/Gethe/wow-ui-source.git .tools/wow-ui-source
git -C .tools/wow-ui-source checkout --detach 8ea15b61e45c0ed4eba01439c90757f86eb78d34
Get-Content .tools/wow-ui-source/version.txt

git clone --filter=blob:none --no-checkout https://github.com/Ketho/BlizzardInterfaceResources.git .tools/wow-resources
git -C .tools/wow-resources checkout --detach 36dd01db2d8fa5086dffda5cbfb3d55f4a70e526
Get-Content .tools/wow-resources/README.md
~~~

注解库使用已审核的具体提交。`Annotations/FrameXML`（界面源码注解）是子模块；普通源码压缩包可能不包含其内容。切换父仓库到选定提交后，执行 `git submodule update --init --recursive`（初始化固定版本子模块），不要使用自动追踪最新版本的参数。父仓库与子模块提交都要保存。[子模块配置](https://github.com/Ketho/vscode-wow-api/blob/d0b5b51fac4c52c493371b9b18e66ce604ea4326/.gitmodules)、[作者生成说明](https://github.com/Ketho/vscode-wow-api/blob/d0b5b51fac4c52c493371b9b18e66ce604ea4326/setup/README.md)

Numy 的 FramexmlAnnotations（界面源码注解）可补模板和混入方法，但作者明确列出继承等支持限制，部分局部混入可能缺失；其 live（正式服）分支会自动跟随上游更新，必须锁定提交，不能视为永久的 12.1 资料。[作者说明](https://github.com/NumyAddon/FramexmlAnnotations/tree/live-mix-into-source)

文档阅读以本地暴雪资料为先；Warcraft Wiki（魔兽维基）的 [API（接口）参考](https://warcraft.wiki.gg/wiki/API) 用于补充示例、历史和行为说明，引用时核对页面版本与目标客户端。它是社区资料，不是已冻结的 12.1 官方手册。客户端也可通过控制台的 `ExportInterfaceFiles code` 导出自身界面代码；这是游戏控制台命令，需以控制台方式启动客户端，不能当成聊天命令。导出属于落地阶段操作，本次未启动游戏或执行导出。[暴雪论坛相关说明](https://us.forums.blizzard.com/en/wow/t/world-of-warcraft-interface-addon-kit-where-can-i-find-please/1798954)

对人工智能的最小使用约定：先查本地 12.1 生成文档 → 查同版本界面调用 → 用注解检查参数 → 对争议行为做游戏验收。用 rg（文本检索工具）按接口名定位即可，暂不建设额外文档服务或向量数据库。资料副本只用于开发，不进入插件安装包；版本记录进入仓库，资料版本变化纳入构建与验证的缓存输入，并通过 PR（拉取请求）审查。

### 2.5 静态检查与运行测试

Luacheck 的 .luacheckrc（检查配置）声明实际使用的魔兽全局量和项目变量。接口定义库不是该检查器的自动白名单；两套工具的环境配置须分别验证。

运行测试使用真实代码，少量断言和一个入口即可。只替代当前测试调用的游戏接口；模拟接口返回普通数字，不代表能验证真实受限值。测试失败必须返回非零退出状态。[Luacheck 配置](https://luacheck.readthedocs.io/en/stable/config.html)、[WeakAuras 局部回归实例](https://github.com/WeakAuras/WeakAuras2/blob/main/tests/README.md)

## 3. 本机技能怎样分工

| 技能入口 | 承担职责 | 不应误解为 |
| --- | --- | --- |
| build-and-verify-init（构建与验证初始化） | 收集需求、展示候选检查、确认并通过正式初始化命令写配置 | 自动安装依赖或建立远端工作流 |
| build-and-verify（构建与验证） | 按仓库配置执行构建和验证 | 自动推断所有业务测试 |
| pr-flow-init（拉取请求流程初始化） | 展示并校验配置、生成本地配置及受管工具链文件 | 已修改远端分支保护 |
| pr-flow（拉取请求流程诊断） | 读取状态并说明下一步 | 已提交、推送或合并 |
| pr-flow-complete（拉取请求流程收尾） | 创建或同步拉取请求、等检查和审查、合并与清理 | 仅创建一个草稿拉取请求 |
| pr-flow-cleanup（拉取请求流程清理） | 按实际合并状态安全收尾 | 强制删除工作树或用户文件 |

上述技能在宿主清单中已安装，不代表目标仓库已初始化。执行时先从技能清单解析当前入口，再读取技能及适用参考文件，避免在仓库中写死插件缓存版本路径。

本机另外有 dev-flow（开发流程编排）技能。它有自己的需求、测试驱动、审查、规格与交付依赖及确认门禁，不是本指南的简称。只有明确选择该完整编排时才按其入口执行，并先检查依赖；不为本次接入构建与拉取请求流程强制初始化整套规格系统。

## 4. 配置唯一构建与验证入口

### 4.1 初始化方式

由 build-and-verify-init 技能完成问答、候选检查、路径与缓存输入说明、环境核查及确认。最终通过正式命令写入 .build-and-verify/config.json，而不是手工覆盖受管配置。

该技能不负责依赖安装或远端工作流；工具准备是前一步单独授权的环境任务。已有配置按技能要求备份和保留，初始化时不顺带改运行器。

候选检查建议：

| 检查 | 初期范围 | 注意点 |
| --- | --- | --- |
| 语言诊断 | 自制插件与真实依赖定义 | 不检查整份第三方插件 |
| 静态检查 | 自有发布代码 | 按实际接口声明合法全局量 |
| 加载清单检查 | 自制插件的清单和引用文件 | 缺文件、错误路径应失败 |
| 素材验证 | 复用 scripts/media/verify.py | 不调用有缺失输入的生成器 |
| 文档检查 | 指南、配置说明、代码示例 | 防止文档改动完全无检查匹配 |
| 运行测试 | 已存在的有效用例 | 没有用例如实记录，不虚设通过 |
| 模拟器回归 | 后续验证过的场景 | 独立检查项，避免掩盖真实失败 |

没有真实构建任务时允许构建检查清单为空，不为了“有构建”增加复制或压缩。打包需求出现后再配置实际构建入口。

每个检查定义：
- paths（触发路径）：什么改动必须重新选择它，包括源代码、测试和相关配置。
- inputs（缓存输入）：什么内容决定旧结果能否复用，包括接口定义版本、工具版本记录、检查配置、测试代码和素材。
- 实际命令、失败状态和必要超时。

范围必须与检查脚本真正读取的内容相符。版本记录或检查器改变后不能继续复用旧代码结果；不把所有检查合成一个大命令来牺牲失败定位和缓存粒度。本地路径或参数发生变化也应能可靠使缓存失效。

### 4.2 日常命令及准确语义

以下命令只有仓库已初始化后才适用：

~~~powershell
build-and-verify build --project .
build-and-verify verify --project .
~~~

build（构建）用于确有构建任务时；verify（验证）默认是按变更选择检查的快速模式。

提交后，固定基线验证使用：

~~~powershell
build-and-verify verify --project . --base <固定基线提交>
~~~

尖括号内容是占位，执行时换成真实提交值。该模式要求工作树干净，基线必须有效；依据固定基线与当前提交的三点差异选择检查。不能与 --full（完整模式）同时使用。

本机当前技能明确规定：
- 本地日常使用快速验证。
- 完整模式只用于拉取请求的远端验证、明确授权的热修复直推，或用户明确说明原因并确认的例外。
- 不为了检查“更全面”自行在本地反复运行完整模式。
- 干净工作区的无基线快速验证可能得到 skipped（跳过），不能据此声称全部通过。
- 正式差异验证要求 status: passed（通过）且 checked（已检查清单）非空；有效缓存命中可报告通过，但应说明使用缓存。
- no_matching_checks（没有匹配检查）应检查覆盖配置，不能默默接受为交付证据。

远端拉取请求验证采用：

~~~powershell
build-and-verify build --project .
build-and-verify verify --project . --full
~~~

构建命令仍按是否存在真实任务决定。完整模式运行全部验证项，不读取通过缓存来跳过检查；“完整”仅指已配置的自动检查，绝不包含未实际执行的游戏验收。

配置超时或总耗时预算时按初始化技能确认，不照搬其他仓库的并发数量。预算超限是性能警告，不等于功能失败；不能减少覆盖以获得好看的时间。

## 5. 游戏验证与人工智能反馈闭环

### 5.1 明确目标客户端与授权部署

在项目说明记录正式服或具体怀旧服分支、构建号和接口版本，来自游戏实际输出：

~~~text
/dump GetBuildInfo()
~~~

该命令在游戏中执行。加载清单里的旧版本字符串不是当前客户端证据。

源码目录与游戏测试目录分开；部署只针对明确的自制插件清单，显示绝对目标路径，覆盖前备份，检查复制结果。工具必须支持预览，拒绝越界目标；不对整个插件目录镜像删除，不清空账号配置。

部署不是构建检查，不放入常规验证或拉取请求自动工作流。只有本次授权包含游戏写入时才执行；已授权范围内无需反复询问。

本仓库涉及 SharedMedia_MyMedia（自定义媒体目录），插件代码和共享素材须分别列出部署范围，缺依赖不能通过自动覆盖第三方文件“修复”。

### 5.2 自动化能覆盖到哪里

| 验证层 | 人工智能可完成的事 | 结论边界 |
| --- | --- | --- |
| 静态诊断 | 接口拼写、参数、类型、代码问题 | 不证明游戏行为 |
| 游戏外测试 | 普通计算、配置迁移、输入校验、局部逻辑 | 不证明完整魔兽接口 |
| 模拟器 | 加载、普通控件行为、截图、模拟状态回归 | 不证明真实服务器和战斗限制 |
| 真实客户端 | 根据可用且授权的手段收集错误、指导或执行可支持的操作 | 没有实际证据就写待验证 |

人工智能不能自动宣称可以控制本机魔兽。当前若只有终端能力，就由人工智能负责实现、部署准备和分析，你执行指定游戏步骤并返回结果。后续存在明确可用的游戏反馈桥接工具时，再核实其权限和能力，不预建自定义远程执行系统。

### 5.3 游戏内调试工具

- BugGrabber（错误收集器）加 BugSack（错误查看器）：复制第一条完整错误及调用路径。
- /etrace（事件追踪）：过滤关注事件，记录顺序和必要参数。
- /fstack（界面层级检查）：定位控件、父子关系和遮挡。
- /reload（重载界面）：部署后重复相同场景；新增资源未生效时完整退出并重进。
- Numy Addon Profiler（插件耗时分析器）：比较相同场景的平均耗时和尖峰；它不需要旧的 scriptProfile（脚本性能采样）开关。[错误工具](https://github.com/funkydude/BugSack)、[暴雪命令源码](https://github.com/Gethe/wow-ui-source/blob/live/Interface/AddOns/Blizzard_ChatFrameBase/Shared/SlashCommands.lua)、[性能工具源码](https://github.com/NumyAddon/AddonProfiler/blob/master/AddonProfiler.lua)

Secret Values（受限值）、受保护操作和安全污染必须分别分析。接口注解或模拟器可能落后于客户端，不能以“类型检查通过”否定真实报错。[暴雪战斗接口说明](https://worldofwarcraft.blizzard.com/en-us/news/24246290)

### 5.4 模拟器按需接入

WoW UI Simulator（魔兽界面模拟器）提供独立测试和自动工作流入口。接入时固定匹配版本，先验证：能加载真实插件；能验证一个实际行为；故意改错后测试失败。截图还要固定窗口、字体、缩放和模拟状态，保存比较结果，不把“输出了截图”当作视觉验收。

只有这些成立才纳入独立检查项。模拟器有缺失接口时先区分工具问题与插件缺陷，不改业务代码去迎合错误模拟。[项目与测试说明](https://github.com/Osso/wow-ui-sim)

## 6. GitHub 与 PR Flow 的一次性接入

### 6.1 先具备远端基础

新仓库建立远端流程前需要（本仓库的实际关联结果见环境使用说明）：
1. 确定远端仓库、所属账号、公开或私有、目标分支。
2. 检查 gh auth status（认证状态）及所需权限，不读取或输出令牌。
3. 确认首次推送的内容和历史：已有本地历史不能因后来忽略文件就认为敏感内容已经消失。
4. 确认 Git LFS（大文件存储）对象和托管额度，远端检出需要实际对象而不是文本指针。
5. 按授权建立或关联远端，并处理首次基线推送。

首次建立远端基线是单独的初始化动作，不能宣称该动作已经通过尚不存在的拉取请求门禁。后续配置变更通过功能分支和拉取请求交付。

### 6.2 初始化 PR Flow

调用 pr-flow-init 技能完成问答、摘要、只读校验、确认和本地写入。它会涉及：

| 文件 | 用途 |
| --- | --- |
| .pr-flow/config.yaml | 目标分支、远端、合并策略、审查门禁和等待行为 |
| .pr-flow/pr-template.md | 拉取请求正文模板 |
| .pr-flow/.gitignore | 运行态忽略规则 |
| .pr-flow/toolchain.json | 可复现工具链身份 |
| .github/workflows/pr-flow-toolchain.yml | 受管工具链工作流 |

不要手工生成工具链身份来绕过初始化校验。开发版工具必须对应远端可以检出的精确实现提交；发布版按工具记录的包和版本恢复。缺少可复现工具链时先处理该问题。

该初始化只写本地文件。分支保护、规则集、允许合并方式和状态检查是远端待办，需要单独授权执行；不能把“生成了配置”报告成“保护已生效”。

### 6.3 远端自动检查

新增仓库业务工作流，例如 .github/workflows/verify.yml（验证工作流），与受管工具链工作流分工：

- 工具链工作流证明工具身份和流程要求。
- 业务工作流安装锁定工具与接口定义，运行本仓库 Build and Verify。
- 初期建议使用 Windows 运行器验证本机脚本兼容性；增加其他系统前确认有实际需求。
- 检出素材时启用大文件获取，确认资源不是指针文件。
- 独立安装所需素材依赖，不把本机已有安装当作远端也具备。
- 使用同一份配置，远端运行完整验证；上传诊断和测试报告，报告收集失败也不能掩盖前面的验证失败。
- 不依赖本机绝对安装路径、插件缓存目录或编辑器扩展目录。
- 拉取请求检查不携带插件发布密钥，也不向游戏安装目录部署。

本机 build-and-verify 技能中关于 pytest-xdist（Python 并行测试插件）的描述不能照搬为所有仓库依赖；只有实际采用相应命令时才需要。当前素材脚本不因接入工具就需要改写为测试框架。

### 6.4 远端门禁设计

建议默认要求通过拉取请求合并，启用真实存在的必需检查名称和讨论解决要求；是否需要他人批准，按可用审查者与仓库权限确认。

先让工作流产生检查，再把实际名称设为必需，不编造名称。必需工作流不能由于路径过滤而永远不启动；工具若报告空跑或配置缺失，工作流必须正确失败，不能只凭任务变绿认定覆盖完成。

单人仓库不能假设作者可以批准自己的请求。可选择由独立审查形成证据、人工确认交付、远端检查强制通过的模式，或安排有权限的另一位审查者；准确记录采用模式，不伪称人工智能审查等同于平台批准。

分支保护可用性受账号套餐及仓库可见性影响，先核实。CodeQL（安全扫描）当前支持列表不包含 Lua，不能将其写成魔兽脚本安全检查；若扫描本仓库 Python 或工作流，应明确只覆盖这些部分。[分支保护文档](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)、[CodeQL 支持语言](https://docs.github.com/en/code-security/concepts/code-scanning/codeql/codeql-code-scanning)

## 7. 一项开发任务的完整执行顺序

| 阶段 | 人工智能执行内容 | 通过标准 |
| --- | --- | --- |
| 需求 | 阅读说明、相关实现和调用方；写清行为、范围、接口依据及验收步骤 | 用户意图明确，高风险取舍已确认 |
| 基线与分支 | 确认工作区改动归属，同步允许同步的目标分支，记录固定提交，建立 codex/ 前缀功能分支 | 分支、工作目录和基线可复核，用户改动保留 |
| 实现 | 一次实现一个行为；可自动复现的缺陷先记录失败再修复 | 小范围差异，有相应测试或实机步骤 |
| 本机验证 | 工作中快速验证；提交后对干净工作树执行固定基线验证 | passed 且 checked 非空，证据对应实际代码 |
| 游戏验收 | 按授权部署；核实版本与依赖，执行相关真实场景 | 记录构建号、步骤和结果，必要场景完成 |
| 审查 | 审查实际差异、数据保留、游戏限制、测试有效性和范围 | 阻塞问题解决；修复后重新验证 |
| 提交与推送 | 只提交任务范围；推送功能分支，核对远端提交 | 本地与远端版本对应 |
| 拉取请求收尾 | 使用 PR Flow 诊断并在授权范围执行收尾 | 当前请求检查和审查满足门禁 |
| 合并与清理 | 通过 PR Flow 合并、同步目标分支、安全删除源分支 | 合并、分支、工作树和清理状态有实际证据 |
| 发布 | 如已授权，再从已合并版本生成并验收最终安装包 | 发布包与源码一致，可回退 |

本机正式验证使用 --base 时必须先提交使工作树干净；如果游戏验收引入了代码修复，重新验证并提交，再更新证据。不能先取干净状态、随后改代码，却继续沿用之前结果。

固定基线在同一任务中保持明确。合并、变基或目标分支更新后，检查实际差异和测试证据是否仍适用，必要时重新固定并记录；不得静默更换比较对象。

可以先创建草稿拉取请求获取远端反馈，但完整验收前不要调用可能自动合并的收尾命令。若只授权创建请求而未授权合并，就停在该授权边界。

## 8. PR Flow 的调用与恢复

### 8.1 本机入口

本次探测没有发现名为 pr-flow 的独立命令，但安装技能的 pr_flow.py（流程脚本）帮助入口可运行。执行时从当前 pr-flow 技能路径定位 scripts/pr_flow.py，先检查帮助，不把源码仓库示例路径直接拼进本仓库。

以下命令中 $prFlowEntry（流程脚本路径）应提前设为实际解析出的入口：

~~~powershell
python $prFlowEntry diagnose --project .
~~~

diagnose（诊断）是只读入口。它不负责提交或推送。

只有完整交付在授权范围内，才调用：

~~~powershell
python $prFlowEntry complete --project . --summary "本次行为变化" --scope "实际修改范围"
~~~

complete（收尾）会创建或同步请求、等待检查、执行审查门禁、合并及清理。它通常不替你提交本地业务改动，也不替代先前的推送步骤；工具链身份变化时存在受管文件自动提交例外，之后仍应核对提交和检查对象。

没有对应问题编号时不添加 --fixes（关联关闭问题参数）。不要为了“流程完整”虚构问题。

### 8.2 常见停止状态

| 状态 | 正确处理 |
| --- | --- |
| PUSH_REQUIRED（需要推送） | 核对分支和提交，在授权范围推送后重试 |
| DISPATCH_REQUIRED（需要触发检查） | 阅读诊断的具体触发要求；确认目标及所需工具实现提交远端可达，再触发或重试，不盲目循环 |
| REPLY_OR_FIX_REQUIRED（需要回应或修复） | 查看失败日志及审查意见，修复后重跑检查、提交、推送，再继续 |
| EXCEPTION_REQUIRED（需要例外决策） | 保留诊断，说明冲突与具体选择，未获授权不绕过规则 |

失败诊断可以使用 gh pr checks（查看请求检查）及 gh run view（查看工作流日志）。不要只重复运行收尾命令，或将远端检查失败归因于“本地已经通过所以应该没问题”。

更新提交后，必须核对最新源码对应的新检查结果。旧提交的绿色状态不能证明新代码通过。未解决的反馈如需对外回复，按会话授权处理，不自动发送无关消息。

### 8.3 合并后的完成标准

报告请求地址及合并结果、目标分支同步结果、源分支删除结果，以及实际工作树状态。只有达到 cleanup_complete（清理完成）并核对实体状态后才报告完整收尾。

本机当前技能默认保留工作树。--remove-worktree（移除工作树选项）只有明确需要时才使用：
- 主工作树不会删除。
- 活跃代理仍在关联工作树中时，工具可能按技能安全保留该目录，并报告分离头状态。
- 不按目录名称猜工作树身份，不强制删除，不把受保护的正常保留误报为失败。

未初始化仓库时不应尝试用收尾命令代替初始化。

## 10. 发布包与回退

BigWigs Packager（插件打包器）是通用魔兽插件打包工具，不要求插件依赖 BigWigs。它生成压缩包、处理依赖和版本信息，并可发布到支持的平台；它不负责拉取请求审查，也不替代 Build and Verify。[作者说明](https://github.com/BigWigsMods/packager)

三者分工：
- Build and Verify：证明已配置的构建与检查结果。
- PR Flow：完成源码的审查、合并和清理。
- 打包器：从指定源码生成和发布安装包。

只有自用复制需求时不必引入自动发布。公开发布时，从已合并的固定版本生成包，排除开发工具、测试、个人配置和日志，安装最终压缩包再验收一次。发布凭据只进入独立发布流程。

代码回退和用户数据回退分别处理；发生配置迁移后旧代码未必能读取新数据。小号也不必然隔离账号级保存变量。游戏运行期间不直接编辑其磁盘配置，避免退出保存覆盖。

## 11. 本仓库落地顺序与验收

| 顺序 | 实施内容 | 阶段验收 |
| --- | --- | --- |
| 1 | 确认检查范围、客户端和本机工具来源 | 自有代码清单、版本与缺口明确 |
| 2 | 独立语言服务器、接口定义、静态检查及解释器 | 正确样例通过、错误样例确实失败 |
| 3 | 通过技能初始化 Build and Verify，接入现有素材验证 | 相关变更能选中检查，失败可定位，缓存输入准确 |
| 4 | 更新项目说明和代理规则，建立必要部署入口 | 不启动编辑器也能完成修改与验证 |
| 5 | 授权关联远端，初始化 PR Flow 和业务工作流 | 本地配置、远端规则和检查分别核实 |
| 6 | 用一个小范围真实改动演练请求流程 | 功能分支、检查、审查、合并、清理证据齐全 |
| 7 | 按实际需求接入模拟器与安装包发布 | 各自通过独立验收，不扩大日常必需依赖 |

整个环境的完成标准不是“装了多少工具”，而是：人工智能能发现错误并定位，验证证据绑定真实版本，游戏特有行为有人实际验收，远端门禁能阻止失败代码合并，完成交付后仓库状态清楚且可回退。
