## Question（问题）

这个插件的哪些部分可以自动化测试、测试放在哪里、如何接入仓库的验证流水线？游戏内人工验收的清单长什么样？

## 调查或讨论范围

仓库已经有成套的验证约束：源码检查（`scripts/dev/check.py` 的 luals／luacheck／toc）、Python 驱动的插件测试（`tests/addons/<插件名>/`）、素材构建与校验（`scripts/media/`）、统一入口 `.build-and-verify/config.json`，以及 `tests/dev/test_inventory.py` 对未登记测试的拦截。新增插件必须登记进去，否则验证不覆盖它。同时仓库明确：**游戏验收不可被模拟替代**。

需要与用户确认的内容：

1. **可自动化测试的部分**：候选是纯函数——角度与填充比例的换算、符文充能比例的计算、配置读写与默认值解释、职业资源映射表。确认哪些值得测、哪些属于"测了也没意义"。
2. **如何把待测逻辑从渲染代码里分离出来**：这是让测试成立的前提。确认是否接受为此把纯逻辑抽成独立模块（即使它只服务于一个功能）。
3. **测试落点与运行方式**：`tests/addons/MYUI_CrosshairHUD/` 的组织方式，以及是否沿用既有的"Python 驱动本机 Lua"做法。
4. **验证登记**：两个插件（公共核心 `MYUI` 与功能插件 `MYUI_CrosshairHUD`）分别在 `.build-and-verify/config.json` 里登记哪些检查、变更匹配路径怎么写。
5. **素材校验规则**：哪些断言写进 `scripts/media/` 的校验脚本。
6. **游戏内人工验收清单**：列出一个"进游戏逐项打勾"的最小清单——包含哪些场景（不同符能／符文充能状态、切专精、死亡复活、解锁拖动、缩放两端、切换 EUI 档案、禁用 EUI 后插件不加载等）。
7. **证据分层**：明确"离线自测通过""原型可行""实机验收通过"三者的区别，避免把前者写成后者。

### 边界

- 本票只定策略与落点，不实现测试本身。
- 不为满足测试而过度设计：只有确实能抓到回归的测试才值得写。

## 关闭条件

- 用户确认测试分层、落点与验证登记方案。
- 人工验收清单成型，且每项都是可观察、可判定的。
- 明确哪些部分**不做**自动化测试及其理由。

## Comments（讨论）

### 2026-09-16 结论

#### 一、测试分层：抽三块纯逻辑，其余靠游戏验收

用户选定：**把三块纯逻辑抽出来做自动化测试**，并明确要求保持轻量——三块放**同一个文件**，不拆成三个。

| 块 | 为什么值得测 |
| --- | --- |
| 角度↔填充比例的换算语义 | 整个渲染的核心契约；原型期只做过一次**不进仓库**的数值验证，将来改公式没有东西拦得住 |
| 符文充能比例的计算 | 调研查出的三个坑全在这：就绪时 `start=0`、空转时整次调用不返回、`duration=0`；另有时钟抖动需钳位 |
| 符文排序规则 | 规则简单（就绪在前 → 充能中按剩余升序 → 空转垫底）但极易被"顺手改一下"破坏 |

**明确不测**：职业资源映射表（v1 只有死亡骑士一行，表太小）；EUI 挂载注入（只能对着 mock 测，而 mock 证明不了真实 EUI 的行为，真正要防的"忘了空值守卫"靠代码审查更直接）；渲染本身（不可能）。

**前提**：这个逻辑文件加载时**不得触碰任何魔兽接口**，否则仓库的 Lua 5.1 测试环境加载不了它。这也是拆分的唯一理由——拆的是"纯计算"与"魔兽接口"的边界，不是按功能拆。

#### 二、落点与验证登记

- **测试落点**：`tests/addons/MYUI_CrosshairHUD/test_logic.py`，Python 驱动本机 Lua 5.1（照搬 `Sim2GSEProbe` 的既有做法）。
- **验证登记**：
  - `MYUI`（公共核心）：当前只有素材，沿用已登记的 `verify.crosshair-media`，待有 Lua 代码后再补源码检查。
  - `MYUI_CrosshairHUD`：登记 luals / luacheck / toc 三条源码检查 + 一条逻辑测试；全部用 `paths` 限定命中范围，不拖慢无关改动。
- **素材校验规则**：已由[素材重导规格](05-media-reexport-spec.md)确定，不重复。

#### 三、游戏内人工验收清单（13 条，用户确认全做）

| # | 验收项 |
| --- | --- |
| 1 | 血弧、符能弧、6 个符文格都按真实数值正确填充，**方向对**（血弧从近 6 点钟那端向上生长，与符能弧镜像） |
| 2 | 花掉 1 个符文 → 该格整格变背景色，再按比例长回来 |
| 3 | **一次花掉 4 个以上符文** → 多出来的显示为整格背景色（不是 1%），且不报错 |

| 5 | 缩放滑块两端（0.5 与 2.0）都正常：不糊、不跑位 |
| 6 | **图层**：打开暴雪设置窗口、打开任意下拉菜单 → HUD 都在其下方 |
| 7 | 默认在屏幕正中；进 EUI 解锁模式 → 出现拖动框、能拖、退出解锁后位置保持 |
| 8 | 切专精、死亡复活、过图 → 不报错、数值恢复正常 |
| 9 | EUI 侧边栏 `MYUI` 分组下出现 `CrosshairHUD` 一行，页面能打开；**行右边的电源按钮能真的禁用它** |

#### 四、性能：不能用纯函数替代观察（用户提问的答复）

用户问：性能观察能不能在纯函数层面解决。**不能，但也不需要。**

- **不能**：纯函数本身几乎零成本（每次几十次三角与算术），在 Lua 里测它等于测空气。真正的开销在 **C 侧控件更新**（遮罩旋转、Cooldown 扫掠）与 **~10Hz 轮询**，这些只能在游戏里观察。
- **不需要正式基准**：量级可解析估出——符文轮询 10Hz × 6 个符文 = 60 次/秒调用；符文格填充随充能连续变化约 60 次/秒旋转；两条主弧只在数值事件时更新，战斗中每秒几次。合计**百来次 C 调用/秒**。对照 EUI 自家资源条跑的是 20Hz 基频、工作量远大于此。
- 因此性能降级为清单第 13 条的**轻度观察**，不做基准测试。

#### 五、证据分层（沿用仓库约定）

**离线自测通过**（纯函数测试）≠ **原型可行**（真实客户端观察）≠ **实机验收通过**（13 条清单）。三者分别记录，不得互相冒充。本清单属第三层。
