# 搜索缓存读取性能修复

Status: ready-for-agent

## Problem Statement

共享结果中心接入后，已完成批次再次参与比较仍读取完整共享批次表，并重复登记本任务、共享缓存及整份状态。实际任务 159 批耗时约 687.6 秒；事后同键读取执行约 39.296 秒，视图准备约 1.4 秒，代表报告写入约 0.17–0.22 秒。此证据证明读取路径不可用，但不能将原生内部统计之外的时间全部归因于数据库。

## Solution

第一阶段同时交付当前任务已核验成绩的内存复用和可用的单键历史读取，去掉重复命中的持久化登记，正确处理坏缓存、存储故障、预算和取消。使用已有真实数据作一次小型存储方案比较；不预先选择或迁移新后端。

## User Stories

1. 作为搜索用户，我希望本轮已核验的同一批次直接复用内存，不再读持久数据或重复模拟。
2. 作为恢复任务的用户，我希望首次引入历史结果仍核对完整请求身份、成绩和统计，且只登记一次使用结果。
3. 作为用户，我希望坏报告可以失效重算，但暂时存储故障不能抹掉已完成成绩并静默补跑。
4. 作为用户，我希望缓存路径同样遵守累计预算和取消，不将这些信号误判为坏缓存。
5. 作为分析和训练调用者，我希望原有完整普通报告、候选关系、诊断开关及共享查询仍正常。
6. 作为维护者，我希望用实际读取性能和管理成本决定是否采用 DuckLake，而不是根据功能列表迁移。

## Implementation Decisions

- 复用既有请求摘要身份、候选缓存、检查点及共享缓存。当前任务仅保存或引用已核验的小成功记录，不长期缓存完整嵌套报告，不另造缓存平台。
- 内存命中采用当前任务已核验快照语义；本任务自身写入新值、失效或失败时同步更新/失效该键，关闭时释放。任意外部同键改写不在热命中时逐次探测；恢复和新任务重新核验。
- 新批次仍先按既有规则成功保存、登记，再进入内存；历史首次导入仍登记本任务。重复使用不重写任务/共享批次和整份状态，不增加独立样本或重复成功批次。
- 通过已安装数据存储技能的逻辑键点读能力定位指定分片，适配器隐藏物理路径。通用多表查询继续供分析训练使用；候选使用其真实存储键，不混用候选身份与记录键。
- 明确的目标缺失、内容损坏或身份/成绩不符才失效；存储不可用及不确定的执行错误保留成功引用并上抛。预算和取消检查不得落入宽泛的坏缓存捕获分支。
- 在批次入口、冷读取及校验后、热返回前检查运行状态。不承诺前后检查能够中断任意阻塞调用；以真实点读延迟和取消观察确定是否需要复用底层连接中断，禁止先建设新线程调度框架。
- 一次性比较当前最小修正、DuckLake、原生 DuckDB。样本为独立副本，比较不授权现有数据接管、迁移或永久切换；不创建长期基准平台。
- 不改两套原生引擎、搜索算法、样本分配、持久化时机或恢复约定。批量预取和集中归档在有相应成本证据后另行决定。

## Testing Decisions

- 最高用户入口是启动真实任务、读取进度/结果、取消及恢复；保留已有页面复制路径。公开程序入口沿用任务启动、读取与恢复接口。
- 复用现有快速引擎接缝，保留真实搜索和任务状态机。测试只增加真实回归需要的少量检查，不固定大量样本或引入新验证框架。
- 核验重复命中的中心读取及持久化登记为零、首次历史导入计数正确、恢复重新校验、损坏重算与存储错误不补跑、取消/预算不将好缓存写成无效。
- 一次性真实数据测量使用已存在的批次和实际命中的 12 个唯一键；记录首次新进程/连接与重复读取，不伪称已清空操作系统缓存。分开连接、执行、获取、校验、写入和总墙钟，保留峰值内存、结果一致性与版本。
- 当前实际数据规模单键冷读取以 1 秒以内为目标；未达标定位剩余成本，不以微基准冒充整次搜索改善。固定候选与种子检查一致性，再用固定预算检查有效搜索量；总时间包含落盘。
- Windows 原生入口和本机统一快速验证使用现有工具，验证预算 60 秒；不把该验证预算套到模拟搜索。云端纯逻辑检查的仓库规则例外须在门禁一明确确认。
