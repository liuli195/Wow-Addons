# 降低历史批量归档开销

## Problem Statement

保原归档批次随着登记对象增多逐渐变慢。当前引用表按对象目标查询时缺少对应索引，同一组归档预览及执行重复查询；压缩还隐式采用 gzip 最高等级9。实际20MB组的归档预览已耗时7至15秒，此阶段尚未开始压缩，不能把全部耗时归因于压缩等级。

## Solution

保持现有数据CLI与完整性保护，用一次最小改动消除引用查询随历史表增长的扫描，并用一个既有代表归档样本比较 gzip6/9 的纯压缩耗时及体积，选择合适的固定等级。新旧归档均继续使用原格式和恢复入口。现已批准的历史占位核实功能保持独立交付，不等待本票。

## User Stories

1. 作为数据所有者，我希望归档已登记历史数据时不为查找少量引用反复扫描全部引用，以免后续组越来越慢。
2. 作为操作者，我希望新根直接具备目标查询索引，以便无需额外设置。
3. 作为操作者，我希望旧根经原预览与批准入口获得相同能力，以免手工修改生产数据库。
4. 作为数据所有者，我希望索引更新遇到占用或空间不足时拒绝且保留原数据，以免提速破坏安全性。
5. 作为操作者，我希望根据真实代表样本选择压缩等级，以便明确速度与体积的取舍。
6. 作为恢复使用者，我希望已有包仍能恢复，新包保持原校验，以免性能变化破坏兼容性。
7. 作为当前批次的操作者，我希望它继续使用已固定的工具直到正常结束，以免运行中变更影响现场。

## Implementation Decisions

- 单票、一个完整的归档提速纵向切片，不拆独立重构票。复用既有初始化、归档和恢复 Interface（接口）。
- 只补引用表目标列索引；不变更引用内容、角色、对象身份、保护规则或自动清理策略，不为其他表提前补索引。
- 新根在既有初始化建表事务中创建索引。旧根复用初始化预览及计划摘要批准，在原根锁、身份核验和事务内按需创建；只读连接不执行隐藏DDL，重复执行不重建已有索引。
- 旧根索引构建先计入实际元数据构建峰值及并发承诺，空间不足或持锁失败明确拒绝；失败不能留下半成品索引或修改用户载荷。复用已有准入能力，不新建迁移框架。
- 压缩只在现有gzip写入处显式固定6级，不新增策略参数或压缩算法。真实已封口代表样本的tar为20,213,760字节：9级0.610994秒/3,435,470字节，6级0.328594秒/3,481,493字节，省0.2824秒、包增46,023字节（1.34%），往返均一致。它只节省每组约0.28秒，主要提速目标仍是引用索引，不宣称整体近两倍提速。
- 现有SHA、包内容核验、恢复验证、锁及物理空间检查保留，不以删校验换速度；当前生产批次运行期间不修改工具或索引。

## Testing Decisions

- 最高公开 Seam（测试接缝）沿用数据CLI：初始化预览/批准后通过归档和恢复入口验证结果；普通动作复用已有进程内main调用，必要真实锁代表保留。
- 复用已有初始化、空间不足及归档往返用例。仅补最小旧schema升级、重复执行和失败保护代表，不加入大样本或长E2E。
- SQLite执行计划及小量内存引用数据作为索引选型诊断证据，不用不稳定的固定秒数做测试门槛，不新增性能测试平台。
- 已完成云端内存查询与合成压缩诊断；真实代表样本已在Windows读取一个既有包并在内存比较，不上传内容、不改生产数据，源包SHA为09a884213132e35373136b675ba2eb43595fa1cd1adf08d377c1fa5ef3aaab14且未变。
- 本机继续固定基线fast和60秒预算，CI按原登记检查；一票完成后统一独立审查。

## Out of Scope

- 不优化其他表或所有查询，不改变批处理脚本、并发模型、归档分包规则、容量政策或保留策略。
- 不重新压缩已有包，不删除原件或恢复副本，不解除真实业务保护，不运行中升级。
- 不修改已批准的历史占位核实交付分支，不为本票迁移既有工具链绑定。
- 不提前写正式规格；交付阶段按MySpec核对可观察契约，必要变更另经完整差异确认。
