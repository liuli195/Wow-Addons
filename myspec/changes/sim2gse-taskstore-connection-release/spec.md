# TaskStore 失败路径的连接释放

## Problem Statement

TaskStore（任务存储）取得 SQLite（轻量数据库）连接后，初始化、角色档案读取、最终进度发布或诊断写入失败时，部分路径没有保证连接关闭。异常及其调用栈可能保留对象，使后续临时目录清理仍受文件句柄影响。

这是独立的连接所有权缺陷。此前 Windows 并发任务及快照失败的原始异常没有捕获；两个节点独立重验通过，不能把本修复写成那些偶发失败或 HUD（准星显示）变慢的已证根因。

## Solution

复用现有 TaskStore、公开任务入口及 SQLite 连接，在四个失败窗口保证释放已取得的连接。正常计算、持久化和错误传播保持；不增加重试、锁、诊断框架或公共存储接口。

## User Stories

1. 作为维护者，我希望任务存储初始化失败仍释放已取得的连接，以免异常对象保留文件句柄。
2. 作为维护者，我希望角色档案读取失败关闭任务存储并保留原异常，以便判断实际失败原因。
3. 作为维护者，我希望最终发布失败仍关闭连接，以便后续正确收尾。
4. 作为维护者，我希望诊断文件写入失败不阻止数据库关闭，以免附加证据影响资源释放。

## Implementation Decisions

- 半初始化失败只关闭已取得的数据库连接，不调用依赖完整属性的 TaskStore 关闭流程。
- 角色档案读取的早期窗口使用局部释放保护，不挪入会统一包装 TaskError（任务错误）的后续处理；缺少任务身份与身份冲突仍按原规则拒绝。
- 最终发布通过现有 finally（最终清理）保证关闭；诊断仅使用内存计数，数据库关闭可先于诊断落盘。
- 不改变状态、HTTP（服务协议）输出、数据模式、事务、锁、缓存、算法、并发或时间预算。

## Testing Decisions

- 使用已有公开 TaskStore 构造/关闭和 run_task（运行任务）入口，共四个短故障检查。
- 复用既有真实 SQLite 连接捕获接缝；只替换对应失败的读取、发布或诊断写入，断言原异常仍可见且 SELECT 1（常数查询）被已关闭连接拒绝。
- 运行任务沿用现有快速搜索边界和一个候选；不运行真实引擎、生产数据中心或长套件。
- 红测自身最终关闭捕获的连接，避免预期失败引发额外清理错误而掩盖证据。
- 云端四窗口红绿及限定独立审查不能替代 Windows 句柄与正式整体性能验收。

## Out of Scope

快照重命名重试或权限调整、原并发失败归因、HUD 或测试调度优化、公共数据中心 API（接口）升级、真实中心扫描、正式规格应用、主干合并和发布。
