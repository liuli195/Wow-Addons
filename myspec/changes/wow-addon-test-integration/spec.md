# wow-addon-test 接入规格

- 变更名：`wow-addon-test-integration`
- 状态：`ready-for-agent`
- 方案依据：`plan.md`（第 8 版，提交 `61f4f5b`），经 ChatGPT 从头到尾完整复审通过

---

## Problem Statement

**从用户视角**：MYUI 准星 HUD 目前只服务死亡骑士，它的生命值、能量、职业资源三块读数
没有与**暴雪原生行为**对照过的自动化验证——仓库里现有的离线测试是**我们自己写的断言**，
不是"和原生应该是什么"的对照。

用户手上有一个测试工具，它沉淀了 **13 职业 40 专精**的用例与**参考期望值**（这些期望来自暴雪原生代码），
正好补上这一层。但工具现在有四个问题：

1. 它是"**工具 + 一个住在别处的技能**"的形态，没有被真正当成一个 Agent 技能，
   导致要额外维护"工具在哪"的指针、安装器和回链；
2. 它**自身有缺陷**：部分用例**没有判别力**——该步骤改变了身份或配置，但被比较的数值一动没动，
   于是一个"完全无视该变化"的实现照样通过，测试**绿得没有意义**；
3. 它的可观测输出与工具标准输出**不对等**（生命与主资源只拿得到角度），
   而工具的比较器**不支持投影**，"怎么比"没有定义；
4. 它的数据文件有 10.9 MB，有被代理误读、大量占用上下文的风险；且自测会改写交付目录里的文件。

---

## Solution

**从用户视角**：

1. **把工具完整做成一个 Agent 技能**——真身只放仓库内的技能目录，Claude 侧用目录连接；
   不再需要定位指针、安装器或回链。工具自身带自检，且**自检必须跟着一起改**（改工具的安全网）。
2. **修掉工具自身的缺陷**：给数据加**第一条检查规则**（判据见下），把没有判别力的用例数据修到有判别力；
   把取值时刻口径、清理适用性、报告输出参数一并做对。
3. **定义清楚"三组件怎么比"**：实际侧取生产代码**真实输出**，参考侧取工具基线**投影**后的结果，
   两边同形比较；**独立期望不得从被测曲线反推**。
4. **把死亡骑士三专精 × 三组件测通**（含需要转换投影的生命与主资源），
   差异按"**通过 + 已知差异**"如实标注，缺口如实登记。
5. **12 MB 只做三件事**：压缩存放、技能文档不指向它、工具统一使用统一输出。

**关键的产出不是"工具被整理干净了"，而是"三组件的真实生产行为能被正确判定、错误能被检出"。**

## User Stories

1. 作为插件作者，我希望死亡骑士的生命值读数被**对照原生语义**验证过，而不是只对着我自己写的断言，这样我换实现时不会悄悄改坏行为。
2. 作为插件作者，我希望能量读数同样被对照验证，这样"换资源类型"这类改动不会被我漏掉。
3. 作为插件作者，我希望六个符文的充能比例与状态被逐格对照验证，因为这是我这个职业最核心的资源。
4. 作为插件作者，我希望生命和能量这两块**即使插件只拿得到角度**也能被验证，而不是因为没有现成数值就跳过。
5. 作为插件作者，我希望"插件与原生策略不同"的地方被**记成通过并标注为已知差异**，而不是被判失败，也不是被悄悄放过。
6. 作为插件作者，我希望**已登记的差异不能被滥用**——同一条用例里如果数值不符合事先确认的产品期望，仍然要失败。
7. 作为插件作者，我希望断线与原生表现的差异被**记为通过并标注为已知差异**（我的插件设计是合理的），并有对应用例验证它在其它方面仍然正确。
8. 作为插件作者，我希望资源类型策略（跟随当前类型 / 固定符能）被显式声明，工具不靠认插件名字挑一个更容易通过的期望。
9. 作为插件作者，我希望工具**不再有"看起来通过、其实什么都没测"的用例**——那会让我误以为测过了。
10. 作为插件作者，我希望这条检查规则**只管已看到的那一类问题**，不要扩展成一套新框架。
11. 作为插件作者，我希望这条检查规则能**长期逐条增加**（像静态检查规则），将来再发现明显问题就再沉淀一条。
12. 作为插件作者，我希望工具能**明确告诉我"哪些字段没有被比较"**，而不是让我以为全都比过了。
13. 作为插件作者，我希望每个用例跑完能知道**清理检查是"已适用"还是"不适用"**，且"不适用"不被算成"通过"。
14. 作为插件作者，我希望同一个技能在 **Claude 与 Codex** 两边都能用，且仓库内装好即可，不装到用户级。
15. 作为插件作者，我希望技能目录**自包含**——工具、参考文档、脚本都在里面，不需要额外的定位文件。
16. 作为插件作者，我希望代理**不会误读那个 10.9 MB 的数据文件**，从而把上下文撑爆。
17. 作为插件作者，我希望工具给代理的输出**有明确上限**，并且**截断的是展示、不是实际执行的测试**。
18. 作为插件作者，我希望**远端 CI 也跑真实工具**，这样行为回退在合并前就能被发现。
19. 作为插件作者，我希望数据文件的行尾在克隆后**不被改变**，否则工具自身的完整性校验会失败。
20. 作为插件作者，我希望重复运行测试**不会改动受版本控制的文件**。
21. 作为插件作者，我希望**改工具**这件事被记录清楚（我们改了哪些、为什么），因为这份工具我们维护自己的分叉。
22. 作为插件作者，我希望这次**只做死亡骑士**，其他职业等真要做时另立规格。
23. 作为维护者，我希望 `AGENTS.md` 里那五个核心技能与既有流程**不被本次改动重写**。
24. 作为维护者，我希望新增的对照测试是**补充**，不替换仓库既有的可见性、读数与配置回归。
25. 作为维护者，我希望这次接好的东西能被**后续全职业扩展**直接复用（工具沉淀的用例库是那个目标的基础）。

## Implementation Decisions

### 形态与目录

- 工具**完整放进技能目录**，`.agents/skills/wow-addon-test/` 为**唯一真身**（提交进版本库）；
  `.claude/skills/wow-addon-test` 为**目录连接**指向真身，**不进版本库**。
- **本仓库的运行不依赖**定位指针、安装器或工具原位置的技能回链：技能就地可用，
  靠自身目录解析路径。（原来的写法是"不要定位指针、不要安装器"，读起来像禁止这些机制存在。）
  **允许**显式的复制安装：把整份技能复制到**另一个项目**的技能目录供其复用，
  目标是项目目录，**不是用户级目录**；这条能力与"就地可用"并不冲突。
- 技能内组织遵循共享规范：入口 `SKILL.md`（只写命令与流程）、`references/`（参考文档）、`scripts/`（可执行部分）、
  其余载荷（数据、运行时、生成器）。
- 路径写法**照本机共享技能的现成做法**：正文只写**相对技能根的路径**，由各代理自行解析。
- 技能头部使用两家都收得下的字段：`name` 等于目录名；
  `compatibility` 作为**兼容性选择**避用（环境要求写进正文与 `metadata`）——
  这是选择，**不是已证实的加载器缺陷**。

### 三组件比较口径（核心）

生产代码实际输出与工具标准输出**并不等同**：

| 组件 | 实际侧 | 独立参考侧 |
| --- | --- | --- |
| 生命、主资源 | 生产代码**实际输出的角度**，经**独立映射**得到比例；另行检查有效性 | 基线或已批准策略的**当前值与上限**，投影为参考比例与状态 |
| 职业资源 | 生产输出的**符文索引、充能比例、状态** | 参考**冷却信息**与**已确定的时间口径**，投影为对应比例与状态 |

**四条不可撤销的约束**：

1. 宿主替身**使用生产代码实际传入的曲线**求值；**独立期望不得从该曲线反推**（否则生产曲线错误可能被消除或绕过）；
2. **不为测试强迫生产代码新增可读比例，也不从输入补造实际输出**（保留现有读数通路）；
3. 从锁定数据**逐条核对**用例、检查点、组件；**缺失观测不得补默认值通过**；
4. 正常通过；**生命、主资源曲线错误与符文／事件更新错误产生预期差异**；恢复后通过
   （这是**少量定向回归**，不是通用变异框架）。

**适配器只加载四个生产文件**（`Logic`/`Elements`/`Config`/`Core`），并在报告中登记与 `.toc` 的差别；
可见性与排序继续由仓库既有回归负责。

### 工具侧要修的地方

| 项 | 决定 |
| --- | --- |
| **数据检查规则库（第一条）** | 定位：**规则库 ≠ 用例库**；规则库是**针对数据本身的机械检查**（像静态检查），可长期逐条沉淀。本次只做第一条 |
| 第一条的两条断言 | **前后可区分**：这三类用例的切换检查点，**本次要验证的那个资源量**必须能与上一检查点**被正式比较规则区分**，无关组件的变化不能代替；**类型可区分**：主资源类型切换时，在**同一份切换后的输入里**，新旧类型的比例必须**能被正式比较规则区分**（不跨时刻）。两条不可互相替代，不需要第三条 |
| "可区分"的判定 | **必须经正式投影与容差判定**，不能只查"原始数值不相等" |
| 适用范围 | **只约束已确认的三类用例的目标检查点**（`primary-type-roundtrip`／`specialization-roundtrip`／`druid-forms`），不推广到所有带切换的步骤 |
| 实现方式 | 在**现有生成器**里给这三类场景安排**合法且可区分**的资源值 + 上述断言；参考答案继续用现有流程生成 |
| 两个小回归 | 前后量改回相同应失败；新旧类型比例改回相同应失败 |
| 修工具的边界 | 数据或基线变更**必须有独立理由并检查生成差异**；**正常测试命令不自动重生成期望**；原有有效场景与回归保留。**修复有证据的工具误报是合法修复** |
| **断线** | **契约已确立**（用户已批准）：插件**不引入原生的断线特殊表现**（填满＋置灰），断线期间照常走既有读数链；与原生期望的差异**登记为已知差异、记为通过**。规格候选见 `.local/spec-work/`（实施期间不改 `myspec/specs/`）。随后补**有判别力的**断线／重连用例；**"必然有差异"仅指当前具有不同预期输出的输入**，不概括所有断线情况 |
| **资源类型** | 保留**动态原生参考**；**另加显式的固定资源策略**，其期望**独立生成**；**不得**靠识别插件名称自动选择更容易通过的期望 |
| **取值时刻** | 根因修在工具侧，**不是加等待**（0.1 秒轮询与检查点存在**相位差**）。区分：模拟器漏跑计时器／事件与登录延迟需要等待（参考与实际用**一致的观察时刻定义**）／连续变化资源的周期刷新。若仍需误差界限，**按充能时长推导，不笼统写"1%"** |
| **清理适用性** | 报告中**正式给出**"已适用 / 不适用"，配置中**必须声明**；**"不适用"与"检查通过"是两个字段**，不得把未执行的断言计为通过；即使适配器失败或超时，**运行器自身的释放仍必须执行** |
| **报告输出** | 工具**正式支持输出目录参数**；默认不修改技能中的受跟踪资产；失败诊断、原始差异与运行身份一并保存 |
| **压缩资产可复现** | 容器内**不得写入生成时刻**：否则重生成字节必然不同，摘要对不上、版本管理出假差异。生成器与维护入口用同一口径，并加自测项看住 |
| **文档不许指向不存在的东西** | 技能文档给出的路径与命令入口**必须真实存在**；目录重排后，旧入口（安装脚本、包装命令）与退役目录名**不得残留**。加检查看住，避免文档随代码一起漂移 |
| **工具自检** | 改工具后**自检必须继续全过**；自检与技能内部自检若为同一套内容，**只登记只执行一套** |

### 12 MB 载荷（只做三件事）

1. **压缩存放**，只有工具消费（工具内部解码，正常运行前不要求代理手工解压）；
2. **技能文档不指向**数据文件（SKILL.md 只写命令，不出现数据路径）；
3. **工具统一使用、统一输出**：正常与异常结果走**同一出口**；被测插件输出**不得直接灌入代理终端**。

**限额要能验收**：规格中固定**总字节上限（16 KiB／次）**；差异预览**最多 10 条**且受总上限约束。
**验收**：一次正常结果、一次大量差异或异常输出**均满足限额**，且保留**真实退出状态、完整计数与"详情已截断"标记**。
**截断的是展示，不是执行中的测试。**
**被截掉的内容必须有处可去**：屏幕输出受预算限制，命令必须能通过 `--output` 交回**未经截断**的完整结果；
凡是会超预算的命令都不得缺这条路——否则就是**静默丢数据**，与"截断的是展示"自相矛盾。
限额检查要有**正面证据**（超限时确实标注并报出省略条数）与**反面证据**（未超限时不得误标截断）。

**明确不做**：权限隔离、产物清扫、逐命令分支审计、发布治理改造。**不宣称"代理不能读取载荷"。**
**Git 存储**：`.gitattributes` 已把压缩格式纳入 LFS，**按现有规则**处理，不另建方案。

### 已知差异的约束

记为"通过"并标注，**但仅适用于事先确认的条件、组件和字段**；
**实际输出必须符合该产品期望**——符合才通过并保留原生差异，**不符合仍失败**。

### 边界（防止"迎合我们的实现"）

| 放进技能的通用能力 | 留作参数或薄适配的项目专属 |
| --- | --- |
| 输入驱动、宿主接口、虚拟时间、投影比较机制、差异分类、生命周期检查、报告与生成流程 | 加载哪些生产文件、从何处观测结果、独立几何映射、固定资源策略、已批准的产品差异规则 |

**独立性取决于依据是否独立，不取决于代码放在仓库侧还是技能侧。**

## Testing Decisions

### 测试接缝（**提请用户确认**）

**最高接缝（首选，唯一的全仓入口）**：`build-and-verify verify --project .`
新增检查在此登记，配齐触发路径与缓存输入；本机 60 秒预算与远端作业超时**分别报告**。

**被测系统的公开接缝**：工具自带的命令入口（`run`），走**真实的生产加载路径与真实的事件/计时器驱动**。

**技能内部的自检**：随技能分发，**在根目录显式登记调用入口**（属目录约定的局部例外），不复制两套实现。

**明确拒绝的三个更低接缝**（否则不构成端到端验证）：
1. 用工具的比较子命令代替运行命令（它不验证生产代码是否真的被加载）；
2. 在测试里直接加载适配器或调用插件内部刷新函数（绕过"生产文件确实被加载"的断言）；
3. 每个检查点强制全量刷新（掩盖漏注册事件）。

### 好测试的标准（本次约定）

- 只断言**外部可观察行为**，不断言内部实现细节；
- **空选择不能通过**；`not_selected` 不计入通过；
- **缺失观测不得补默认值通过**；
- 差异**必须经正式投影与容差判定**，不能只看原始值；
- **截断展示不得减少实际执行的用例数**；
- 失败、超时、缺依赖分别报告，**跳过不记为通过**。

### 要测的模块与既有先例

| 被测对象 | 先例 |
| --- | --- |
| 技能加载与定位（两代理、含目录连接、失败传播、用户级不落盘） | `tests/dev/` 现有开发检查器回归 |
| 三组件对照（真实生产文件 + 双边投影 + 定向缺陷） | `tests/addons/MYUI_CrosshairHUD/` 现有离线读数测试 |
| 输出限额与报告新鲜性 | 新增；沿用统一验证入口的登记方式 |
| 工具自检与数据规则 | 工具自带自检 + 第一条规则的三个小回归 |

**所有实施票据都沿用 TDD 与独立审查。**

本次独立审查统一由 ChatGPT 承担，并同时完成最终验收；不再另跑一套重复的本地代码审查代理。

## Out of Scope

- **其它职业的功能开发**（本次只做死亡骑士；工具覆盖 13 职业 40 专精 ≠ MYUI 支持 40 专精）；
- 画面、布局、像素与视觉排序验证（工具明示关闭视觉排序；排序由既有回归负责）；
- 受限上下文（秘密值）、污染、受保护操作、战斗锁定权限；
