# 04：解锁模式绕过条件

Triage（分拣）: ready-for-agent
Status（状态）: closed
Assignee（领取者）: Codex（主代理）
Parent（来源）: [Crosshair HUD 可见性规格](../spec.md)
Blocked by（前置事项）: 02：可见性条件生效，且两处一致

## What to build（要做出什么）

把条件设成「仅战斗中」，人却在主城——打开解锁模式，照样拖得到准星。

- 解锁模式中，**条件判定为隐藏时绕过**：元素照常显示、可拖动。
- 但「这东西不该存在」的情形不绕过：**总开关关着**、或**可见性选了「从不」**，解锁模式里也不出拖动框。

这条规则要的是：让「现在是编辑模式」与「这东西被关掉了」区分开。前者该让你调，后者不该冒出一个空框。

## Acceptance criteria（验收条件）

- [ ] 条件为「仅战斗中」且不在战斗中，进入解锁模式 → 拖动框存在且可用
- [ ] 同场景下关掉总开关 → 拖动框消失
- [ ] 同场景下把可见性设为「从不」→ 拖动框消失
- [ ] 退出解锁模式后行为复原（该隐藏的仍然隐藏）
- [ ] 复用 EUI 现成的解锁中标志，不新造一套判定
- [ ] 离线检查通过

## Comments（讨论）

**完成证据**（提交 `6961185`，修复见审查修复提交）：红灯为「解锁模式下条件必须让路」，实现后转绿。固定基线完整验证 `status: passed`。

**票据边界说明（经独立审查指出）：** 提交 `6961185` 里除了本票范围，还捎带了**旧标量兜底链**的修复。那不是范围蔓延——兜底链是规格〈补充说明〉里的**必需项**，是票据 02 做错、在本票被测试抓出来的：EUI 对「只勾了一个条件」的情况一律交回「空」，初版把「空」当成「显示」，导致只勾「仅战斗中」时条件静默失效。它落在这里是因为**测试是在写本票的红灯时才暴露出这个问题的**。属于票据边界错位，补记于此。

**一段被删掉的重复（经独立审查指出）：** 初版在委托 EUI 判定之前又本地短路了 `never`／`always`。核实 EUI 源码后确认它自己的判定函数本就认这几个标量（末尾即 `-- "always" and "mouseover" both return true`），本地短路是第二处需要跟着 EUI 同步的副本，**已删**——条件语义全归 EUI。

**同一条装配入口上的其余断言：** 本票还用「总开关关着时解锁模式也不显示」覆盖了「关掉状态不让路」的另一半（那半条票据 02 已天然覆盖）。
