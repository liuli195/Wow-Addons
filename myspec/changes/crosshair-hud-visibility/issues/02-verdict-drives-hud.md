# 02：可见性条件生效，且两处一致

Triage（分拣）: ready-for-agent
Status（状态）: closed
Assignee（领取者）: Codex（主代理）
Parent（来源）: [Crosshair HUD 可见性规格](../spec.md)
Blocked by（前置事项）: 01：地基：可见性模块、接线与降级

## What to build（要做出什么）

翻转可见性判定，准星真的会消失；而且**屏幕上的它**和**交给 EUI 的那张拖动框**是同一个答案。

- 可见性判定驱动准星的显示与隐藏。
- **渲染侧**（画不画）与**解锁元素侧**（给不给拖动框）都由**同一个出口**回答——消掉现有那两处「各写一遍总开关判断」的重复。
- 总开关关掉时：不显示，且解锁元素报告隐藏（**不留可拖动的空框**）。
- 降级：认不出来时照常显示。
- 演示模式绕过可见性条件，照常显示（与它现在绕过总开关一致）。
- 配置默认值显式为「总是」，使旧存档升级前后行为不变。

## Acceptance criteria（验收条件）

- [ ] 翻转假 EUI 的判定 → 准星框体的显示状态随之改变
- [ ] **同一次翻转**下，交给 EUI 的解锁元素报告的隐藏状态，与框体的显示状态一致
- [ ] 现有两处重复的总开关判定被消除，两处问同一个出口
- [ ] 总开关关 → 框体隐藏，且解锁元素报告隐藏
- [ ] EUI 缺失或接口认不出来 → 仍显示，不报错
- [ ] 演示模式开启时绕过可见性条件，照常显示
- [ ] 没有可见性配置的旧存档，行为与升级前一致
- [ ] 脚手架：框体 mock 的显示函数由空实现改为记录状态（唯一需要的脚手架改动）
- [ ] 测试打在**装配入口**上（按清单顺序加载 → 假 EUI → 触发登录 → 翻转判定 → 断言），不是打在内部函数上
- [ ] 离线检查通过

## Comments（讨论）

**完成证据**（提交 `362ad46`，修复见 `4 号票据之后的审查修复提交`）：红灯为「判定为隐藏时，框体必须从屏幕上消失」，实现后转绿。固定基线完整验证 `status: passed`。

**两处票面与实现的偏差，经独立审查指出后已处理：**

1. **验收项「脚手架：框体 mock 的显示函数由空实现改为记录状态（唯一需要的脚手架改动）」当时并未执行**——实际做法是另写了一个带自有 harness 的新测试文件，因此没动既有的解锁元素测试。审查指出这会让两套夹具各自漂移。**已按票面补做**：既有夹具的显示函数现在也记录状态。
2. **「无可见性配置的旧存档等价于『总是』」这条在实现时被做错**：EUI 对「只勾了一个条件」的情况一律交回「空」（单个条件存在旧标量里，由调用方兜底），而初版把「空」当成了「显示」。后果是只勾「仅战斗中」时整个条件静默失效。**这正是规格〈补充说明〉预先警告过的「把空当成显示会跳过整条兜底链」**，到票据 04 才被测试抓出并补全。

**夹具忠实性**同样经审查修正：初版夹具让 EUI 对旧标量也返回判定，与真实契约不符——夹具不忠实的话测试会绿而实机静默失败。现已改为忠实模拟（多选走共享引擎、单选取旧标量），并让它可翻转。

## Comments（讨论）· 实机验收

**部署**：`Codex（主代理）` 将本插件全部文件复制到游戏目录 `Interface\AddOns\MYUI_CrosshairHUD\`，逐文件核对一致；旧版备份于 `.local/deploy-backups/MYUI_CrosshairHUD-20260918-043120/`。核心插件 `MYUI` 无需更新（未改动）。

**第一轮实机结果：发现一个静默失效缺陷（离线全绿）。**

用户报告：勾选**目标／敌对目标／骑乘中／御空术坐骑**全部毫无反应（总开关本身正常，用户后续更正了最初「总开关失效」的措辞）。

**根因**：可见性判定链只实现了**一半**。EUI 自家消费者（资源条的 `ShouldShowSecondary`／`ShouldShowBar`）的顺序是三步——① 选项通道的隐藏否决、② 多选模式集、③ 旧标量兜底；初版做了 ②③ 而**整条漏掉 ①**。而条件分三类（`mode`／`group`／**`opt`**），其中 `opt` 那一整类**只存在于选项通道的字段里**（`visOnly*`／`visHide*`）：目标、敌对目标、骑乘中、御空术坐骑、副本、住宅、休息中、载具——全部因此静默地什么都不做。

**这正是本项目反复强调的那类错**：离线测试全绿，因为它只覆盖了**已实现的那两步**；漏掉的那一步没有任何东西为它说话。离线证据在这里**结构性地**覆盖不到——除非有人先知道链有三步。

**修复**（提交 `f4ef5b8`）：按 EUI 的顺序补上第 ① 步。测试**先复现实机现象**再修（红灯文案即用户报告的症状）。

**逐条比对结论**：修复后本插件的判定链与 EUI 各消费者等价。一处差异已核实为**无活缺口**——消费者各自的旧标量链还认 `combat` 与 `target` 两个**旧版遗留别名**，而 EUI 9.1.8 的行定义里 `combat` 格子写出的是 `in_combat`、目标类走选项通道不写标量，故这两个值进不了本插件的存储（且本插件存储为全新、无历史数据）。

**第二轮实机结果：用户确认通过。** 复核了第一轮失败的全部条件（敌对目标／目标／骑乘中／御空术坐骑／副本），并回归确认「仅战斗中」「从不」「演示模式」「解锁模式里可拖动」均未被本次改动影响。

**证据分层**：本节的结论属**游戏内人工验收**，不可由离线测试替代；反之离线那几条也不能由这次冒烟替代。两者各自成立、互不冒充。
