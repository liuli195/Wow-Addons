# 人工起点训练显式四并发

## Problem Statement

人工起点训练的同层候选评分被限制为最多两个单线程引擎。维护者希望在不打断当前五目标训练、不改变评价规则的前提下，明确选择四并发并用相同工作量验证实际收益。

## Solution

训练 `run`（运行）入口接受 `--max-processes`（同时评分上限），默认仍为2，允许显式选择4。复用现有同层评分执行器，仍按候选原顺序消费完整成绩，整层结束后筛选。普通搜索默认及显式可选上限均保持2。新代码或并发配置进入既有条件身份，新旧条件不混用成绩，不恢复旧规则任务。

## User Stories

1. 作为维护者，我希望人工训练可显式选择4个单线程评分进程，以验证同层评分的收益。
2. 作为现有使用者，我希望省略新参数时仍为2并发，以保留现有默认行为。
3. 作为维护者，我希望非法并发值在计算前被拒绝，以避免不受控资源使用。
4. 作为维护者，我希望乱序完成的候选仍按原顺序使用成绩，以保留评分和筛选规则。
5. 作为维护者，我希望取消、失败和恢复仍保留完整成功批次，以避免丢失结果或重复计算。
6. 作为维护者，我希望不同并发条件分别记录，以避免跨条件误用旧成绩。
7. 作为维护者，我希望用相同候选、样本和随机条件对照2与4，以区分调度收益和增加工作量。
8. 作为维护者，我希望本机当前五目标训练继续原条件运行，以避免开发干扰现有计算。

## Implementation Decisions

- 使用现有同层候选评分执行器；仅训练路径允许现有配置的合法上限为4，普通任务、恢复和双场入口仍校验最多2；不引入新调度器或依赖。
- 训练公开命令、训练公开调用及实际训练配置显式传递并发值；所有默认值保持2。
- 每个引擎仍使用1个线程；同层结果顺序、整层后筛选、晋级复核和独立复测保持原行为。
- 每候选600秒预算、16候选完整轮次、连续两个完整无改善轮次、候选总上限保持。
- 现有训练条件已包含实际配置和全部规则源码摘要；沿用该身份规则，不增加例外复用或存储。
- 云端沿用当前工作树和固定基线，拟新建 `codex/seed-training-parallel-four` 功能分支；不修改本机当前训练工作树。

## Testing Decisions

- 唯一最高层公开接缝为训练命令入口 `seed_training.main`（人工起点训练命令）。从 `run --max-processes 4` 穿透到真实训练配置和同层候选评分。
- 复用现有构造角色、真实独立数据中心测试副本和引擎外部边界；不伪造产品内训练、评分或条件身份实现。
- 先通过该入口取得最小失败检查，再做最小实现，再运行同一检查转绿。验收显式4、默认2、非法值、最大同时评分数和原顺序消费；兼容性检查确认普通任务、恢复及双场入口显式4仍拒绝。
- 复用已有取消、失败、恢复检查，并核对并发变化导致条件变化及旧条件不可原地恢复。
- 同工作量对照使用同一分支、角色、候选顺序、随机条件、样本量和预算，分别取2及4；工作目录和训练条件独立。比较相同完整评分批次数、样本数、成绩与顺序及耗时，失败和取消不记为性能成功。
- 云端只记录实际可执行的检查，不将Linux（云端系统）替身诊断当Windows（目标系统）真实引擎验收。现有命令依赖Windows锁及受检引擎；本机专项验证由隔离分支执行且不得干扰当前训练。
- 正式验证使用现有统一入口、干净提交和固定基线；缺工具、平台不兼容与未运行分别报告，不能以跳过冒充通过。

## Out of Scope

- 跨材料、跨场景调度，独立复测六批并行，新存储、任务身份例外、评分或收敛规则修改。
- 普通搜索默认四并发，预算增加，调整引擎线程数，完整材料重训。
- 中断当前本机训练，切换本机运行代码，合并主干、正式发布或修改远端设置。
